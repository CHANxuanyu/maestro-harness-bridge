# 原生历史性能验收

任务三的可重复入口：

```sh
npm run test:performance -- src/__tests__/performance/NativeSessionStorage.test.ts --disableConsoleIntercept
```

只运行指定的主进程性能文件，使用现有 `vitest.performance.config.mts`。不需要账户、CLI、桌面或网络。测试创建独立临时目录，隔离 Electron 数据目录和提供方 home，结束后删除生成数据。它不会读取用户的原生账户目录，也不会把样例或对话内容写入仓库。

## 样例与测量方法

生成器是 `scripts/native-performance-fixtures.cjs`，复用 `e2e/fixtures/native/protocol.cjs` 的原生编码器。格式来源为锁定的 Codex `rust-v0.163.0-alpha.11.1` 和已验证的官方 Claude Code `2.1.310` 包，具体源码及验证见编码器注释与原生端到端完成记录。每轮包含用户请求、两个独立工具调用及结果、最终回答，共四条可见消息。

两家分别生成 1 万、5 万条可见消息，包含 50% 工具调用；另生成两个 53 MiB 工具结果组成的超过 100 MiB 转录，以及单个项目的 5000 个会话。每个测量固定采样三次，失败不重试。数据生成、断言、结果序列化都在主进程读取计时之外。

测量返回值的 JSON UTF-8 字节数和 V8 序列化字节数，作为 IPC 数据量的可重复估计；它们不包含 Electron 帧开销，也不代表渲染器接收或绘制耗时。每次验证消息数量、模型、增量与完整读取一致性，以及搜索命中，防止用丢数据换速度。

首次读取指新建 storage 实例的首次读取，不清除操作系统页缓存。增量读取在同一实例上追加一轮，分页使用已预热的实例。历史扫描区分元数据冷缓存与预热后的读取。所有数字只能与相同样例、运行环境及缓存条件比较。

| 项目下 5000 个会话的历史扫描或列表分页 |  5000 ms |              记录实际值 |
| 项目下 5000 个会话的内容搜索           | 10000 ms |              记录实际值 |

预算在运行基线前写入测试：打开会话容许秒级工作，持续跟随应在 150 ms 内完成，已缓存的分页应在 50 ms 内完成。搜索预算较长，因为需要实际检查所有会话正文。这些是本轮固定环境的工程验收预算，不是所有机器的响应时间承诺。

另外记录界面已加载全部 5 万条消息时的读取及返回量；保留调用者要求的完整结果，不在后端悄悄缩小 `limit`。

第一次运行中 Claude 的全局元数据缓存只在首次扫描时是冷的，后两次 80.9/62.3 ms 是暖读，不能与冷扫描混比。最终用例已在每次扫描前清除临时目录内的磁盘缓存，并通过已有测试接口重置 Claude 的内存缓存，因此后三次都是冷扫描。Codex 的前后三次一直清除了磁盘缓存，工具解析和搜索修复的比较条件一致。首次整套运行的 Vitest 控制台截获只保留了 Codex 的数字；随后单独运行 Claude 并关闭控制台截获补齐基线。最终完整两家用例同样关闭截获，2/2 通过，耗时 20.75 秒。

只修两处实测热点：Codex 工具结果配对改为单次解析内的 ID 索引；搜索把本次扫描的路径传给原有正文读取，仍用原来的搜索筛选、预览和计数。没有持久化新索引或缓存，没有哈希，没有改原生转录。40 会话的额外真实文件系统回归在修复前枚举目录 164 次，修复后至多 8 次；旧文件名及并行的不同项目搜索保持正确。两处时间预算失败回归均在产品修复之前运行。

最近 500 条和大工具转录的返回值都低于每次 1 MiB 预算。全部历史请求完整保留调用者要求的数据，它不算“最近 500 条”预算通过。`refreshNativeConversation.ts` 使用 `max(500, tab.logs.length)` 并在未找到锚点时扩大范围，已加载全部 5 万条时，后台只读分页虽在 1 ms 左右返回数组，序列化后仍有约 20 至 22 MB。没有测量真实渲染耗时，不能据此宣称界面已经卡顿。

Opus 可运行本文件开头的命令，比较 `50k/increment` 与 `50k/loaded-tab` 的返回量，再在前端评估缩小刷新窗口及稳定 ID 合并。验收应继续覆盖相同正文的不同回合、晚到工具结果、阅读位置、草稿和未读数。后端本轮不静默限制 `limit` 或漏掉历史消息。

## 仍然存在的限制

两家的元数据扫描都有既有 100 MiB 文件上限。测试明确证明超过此大小时 `listSessions` 不发现该文件；按已知 ID 打开仍能正确读取、压缩工具输出并增量跟随。依赖项目历史枚举的搜索也无法发现这个大文件。移除此产品上限不是本轮性能修复，不能把已知 ID 读取通过宣称为完整的历史发现通过。

这组样例的解析后可见内容都低于既有 32 MiB 游标上限；超过 100 MiB 的一组是巨大工具输出，经已有压缩后保留。解析后仍超过 32 MiB 的正文或图片会沿用完整读取，不在本轮增量预算通过的结论内，最多两份游标的限制未改。

没有覆盖 SSH 大数据、真实账户、macOS 或桌面 Codex；也没有测真实原生 CLI 在这些数据规模下的启动和生成耗时。操作系统缓存未清空，单线程事件循环阻塞、主进程峰值 RSS 和渲染器绘制不包含在这些时间预算内。数据量、结果一致性及原生文件 size/mtime/ctime 不变都有断言；没有把压缩后的缓存写回原生文件。

## CI 建议

建议先由独立的手动或定时 Linux 作业运行上述命令，在固定 Node 版本与 runner 规格下收集基线。使用一次执行、零自动重试，临时数据不上传，只保留数字报告。确认机器差异之后，再由用户决定是否加入合并前必过检查。本轮不新增性能 CI 作业，不改 rulesets，也不把本地预算假装成已有 CI 的验收结果。
