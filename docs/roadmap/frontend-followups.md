## 工作清单与验收目标

### 1. 运行中命令的实时输出

- **依据：** 后端现在会推送运行中命令的累计输出：同一调用 ID 的 `running` 事件携带 `toolState.output`，渲染层按 `tool-${id}` 合并进同一条记录。但界面不会更新：`LogItem.tsx` 的 memo 比较只看 `toolState.status`，`sameSubagentLogs()` 也只比较 id、文本和状态；运行中只有输出在变，所以命令结束前都不会重渲染。另外 `ToolCallDetails.tsx` 的结果块固定 20rem 高度、内部滚动，输出超过一屏后用户停在开头，看不到最新输出。
- **做法：** 在渲染链的比较函数里加上 `toolState.output`，包括 `LogItem` 自身、`sameSubagentLogs()`，以及折叠行传入子行时用到的比较。工具仍在运行时，结果块用规范工具 `useStickToBottom()` 跟随最新输出，用户上滚后松开。不改折叠规则，不新增卡片样式。
- **验收：** 用合成事件序列驱动同一调用多次运行中更新：展开的结果块逐次更新并贴底；用户上滚后不被拉回，滚回底部恢复跟随；完成后的状态和最终输出正确，没有重复卡片。运行中的回合仍保持展开（既有规则）。

### 2. 历史消息的模型与思考等级

- **依据：** `SessionMessage` 现在带原生 `model` / `effort`：Codex 的正文、推理、工具消息都带；Claude 只带 `model`；用户消息不带。`transcriptMessagesToLogEntries()` 还没有映射，消息信息里历史回复仍显示“未记录”。另有一个混用问题：实时回合的 `turnModel` 来自 `customModel`，可能是别名（如 Claude 的 `opus`）或缺省；原生值则是完整模型 ID。两者相邻时，`computeTurnSettingChanges()` 会把“别名对完整 ID”误报成换了模型。
- **做法：** 在 `transcriptMessagesToLogEntries()` 把原生值映射到 assistant 侧条目的 `turnModel` / `turnEffort`。给条目记录来源（发送时打的戳，或原生记录），`computeTurnSettingChanges()` 只比较来源相同的两个值。合并时沿用 `withRendererFields()` 的规则，实时戳优先。缺省保持缺省，不用当前设置补。
- **验收：** 重新打开的 Codex / Claude 历史，在消息信息里显示原生模型（Codex 另显示思考等级）。同一来源内中途换模型，只在第一条新回答处提示一次；实时别名与历史完整 ID 相邻时不误报；没有记录的仍显示“未记录”。

### 3. 对话布局的未读计数

- **依据：** `useTerminalOutputScroll.ts` 用显示行数的差值计未读（`filteredLogsLength`）。回合结束后过程折成一行，行数变少，已读基线反而大于当前行数，计数被清零或偏小。hb.4 把这记为已知取舍。
- **做法：** 只改对话布局：按行 ID 记住读到的位置，只把之后新出现的用户消息和回答（`isFeedReplyRow()`）计入未读；工具、进度、推理不计，折叠和展开都不改变计数。智能体布局保持现状。
- **验收：** 上滚阅读时，新回答和新消息使计数增加；回合结束折叠后计数不减少；回到底部清零；切换页签再回来计数正确；第 5 项自动刷新追加的内容同样计入。

### 4. 对话布局下的“显示工具调用”开关

- **依据：** `TerminalOutput.tsx` 用 `toolsVisible || readingColumn` 决定工具行，对话布局下这个开关实际不起作用，但设置页（`ThinkingModeSection`）照常显示，用户切了没反应。
- **做法：** 不给它新增行为。对话布局下，设置页把该开关标为不适用，并说明工具调用已收进每轮的折叠行；中英文案都加。智能体布局不变。
- **验收：** 对话布局下开关显示为不适用且有说明；智能体布局下行为不变；设置搜索仍能找到这一项。

### 5. Claude Code 自动刷新的阅读体验

- **依据：** PR #4 让 Claude 会话也像 Codex 一样后台跟随，只更新 `logs`，不改阅读位置和未读字段。Codex 跟随时的前端行为（外部更新不抢位置、在底部时跟随）此前已经验证过。
- **做法：** 沿用 Codex 已验证的规则，补 Claude 的回归。只有发现 Claude 特有的差异才修改，例如工具结果后到时应该更新已有卡片，而不是新增一行。
- **验收：** 在底部时新内容自动可见；上滚时位置不动、未读按第 3 项增加；草稿、队列和其他页签不变。

### 6. 历史摘录的显示

- **依据：** Codex 页签以及 Claude TUI / Dynamic 的历史条目，现在是该轮最终回答的首段（最多 500 个字符），不是模型写的摘要，也没有持久化的来源字段。
- **做法：** 不加区分标记。内容就是回答原文，不会误导；要区分得先扩展历史存储契约，收益很小。只检查历史列表和详情弹窗在显示截断摘录时排版正常，比如截在代码块中间不会让后面的内容破版。
- **验收：** 摘录条目在历史列表和详情里正常显示；含 Markdown 的截断摘录不破版。

### 7. 窄窗口下的主面板头栏

- **依据：** hb.3 / hb.4 的已知限制：窗口较窄时主面板头栏被整体裁切。桌面窗口的设计最小宽度是 1000px（`DESIGN_MIN_WINDOW_WIDTH`），屏幕更小时还会再低；左右侧栏展开后，主面板实际宽度远小于窗口宽度。
- **做法：** 先在最小窗口宽度、左右侧栏都展开的情况下复现，确认哪些控件溢出。参照 [Left Bar 头栏的宽度让位规则](../agent-guides/UI-PATTERNS.md#left-bar-header-width-gates)，给主面板头栏定出让位顺序：标题省略显示，可点的控件不被裁掉。不做整页重设计，手机布局不动。
- **验收：** 窗口宽 1000px 且两侧栏展开、以及更宽的几档下，头栏控件都可见可点，长标题省略显示；手机布局截图不变。

### 8. 侧栏打开会话后的输入焦点（Issue #1）

- **依据：** Issue #1 记录了代码审查时的怀疑：在项目会话列表里点击或按 Enter 打开会话后，事件冒泡可能把焦点抢回侧栏。至今没有实机确认。
- **做法：** 先写测试复现点击和 Enter 两种情况。复现了才修，只改冒泡或交还焦点的那一处，复用 `useFocusAfterRender()` 等既有工具；没复现就在记录里写明，不改代码。
- **验收：** 打开会话后焦点在输入框，可以直接打字。

### 9. Issue #1 整理与实机验收清单

- **做法：** 按 hb.3、hb.4 和本阶段的证据，更新 Issue #1 的勾选状态，剩余项链接到本计划。列出需要用户在 macOS 上执行的实机回归：长回合、停止后恢复、共享模式双向刷新、滚动锚点、运行中命令输出、Claude 跨应用刷新、窄窗口头栏。
- **验收：** Issue #1 的状态与实际证据一致；实机清单写进完成记录，每一步可以照着做。

## 完成记录

环境：Linux 云容器。除组件测试外，第 1、7、8 项另在本容器里用 Xvfb 运行的开发版 Electron 应用中核对：使用临时演示数据目录和合成会话，不接触真实账户；截图和测量只留在本地。这不是 macOS 实机验收。

### 1. 运行中命令的实时输出

- 计划里“`LogItem` 不重绘”的判断有误：它的比较函数已按 `toolState` 对象比较，后端每次合并都会生成新对象，运行中的输出本来就会刷新。真正的问题只有结果框不跟随：输出超过 20rem 后，读者停在开头。
- 改动：调用仍在运行时，结果框用 `useStickToBottom()` 跟随最新输出，读者上滚后松开；已完成的调用照旧从顶部打开。没有改 `LogItem`。
- 回归：贴底跟随、上滚后不被拉回，修改前失败、修改后通过；已完成调用从顶部打开、输出合并刷新两条保留为护栏。实机模拟输出增长三次，滚动位置每次都等于最大值；滚回顶部后输出继续增长，位置保持 0。

### 2. 历史消息的模型与思考等级

- 改动：`transcriptMessagesToLogEntries()` 把原生 `model` / `effort` 映射到回答条目的 `turnModel` / `turnEffort`，并以 `turnSettingsSource: 'native'` 标记来源。与实时回合一样，只有回答正文带这两个值，推理、工具和用户消息不带。合并时发送时打的戳整组优先；之前缓存里没有戳的回答，刷新一次后补上。`computeTurnSettingChanges()` 只比较来源相同的值，实时别名（如 `opus`）与原生完整 ID 相邻时不再误报换模型。
- 回归：5 条，修改前均失败，覆盖映射、缺省、合并优先级、折叠时保留来源和跨来源不误报。

### 3. 对话布局的未读计数

- 改动：对话布局改为按回合折叠之前的列表计数，从同一个起点开始，只计用户消息、回答、进度说明和错误；工具调用和推理不计，折叠后计数不变。智能体布局不变。
- 与计划的差异：计划写的是只计消息和回答。进度说明仍然计入，因为它是智能体写给用户的话，每轮只有几条，原有行为和测试都依赖它。错误也计入，因为路线图要求错误立即可见。真正的噪音（工具和推理）已经排除。
- 回归：运行中两次工具调用不增加计数，回合结束折叠后计数保持 2，修改前失败。原有 357 项滚动、补载和未读测试在两种布局下全部通过。

### 4. 对话布局下的“显示工具调用”开关

- 改动：会话列表视图下，设置页在该开关下面加一句说明：工具调用已收进折叠行，这个开关只在“管理智能体”视图中生效（中英文案）。开关没有禁用，因为它对智能体布局仍然有效。设置搜索不受影响。
- 回归：两条，会话列表视图显示说明且开关可用，智能体视图不显示。

### 5. Claude Code 自动刷新的阅读体验

- 结论：不需要修改。`TerminalOutput` 的滚动和未读逻辑不区分提供方，Codex 已验证的规则同样适用于 Claude。Claude 特有的“工具结果写在后面的消息里”，在刷新时原地更新已有卡片，不会多出一行。
- 回归：结果后到时原地更新、停止的调用显示为已停止，两条直接通过，作为护栏保留。

### 6. 历史摘录的显示

- 问题：摘录取回答第一段，按空行切开。回答以带空行的代码块开头时，摘录停在代码块中间，缺少收尾的三个反引号。详情弹窗显示正常，但历史列表用的 `stripMarkdown()` 只处理成对的代码块，会露出 ` ``` ` 符号。
- 改动：`stripMarkdown()`（`src/shared/markdown.ts`）在处理完成对的代码块后，去掉剩下的围栏行，保留代码内容。
- 回归：未闭合、正文后接未闭合、成对加未闭合三种情况，修改前失败。

### 7. 窄窗口下的头栏

- 实测：主面板头栏本身不裁切。窗口 1000px、两侧栏展开、头栏带满会话 ID、费用、上下文和长标题时，标题省略显示，各控件都在。窗口变窄时应用还会自动收起两侧栏。
- 真正被裁的是右侧栏：窗口 1000px 时，左栏 256 + 主面板最少 400 + 右侧栏 384 超出窗口，右侧栏被挤出约 40px，头部收起按钮、文件工具栏和底部状态栏都看不到。三者最小值之和（256 + 400 + 360 = 1016px）也大于设计最小宽度。改动：右侧栏的宽度设置只是偏好，不是下限，空间不够时允许缩窄，保存的设置不变。实测 1000px 时右侧栏为 344px，所有控件可见；1600px 时仍为 384px。
- 同宽度下另发现输入框工具栏重叠：左组按钮用 `flex-1`，换行时被当成 0 宽，右组不换行，左组被压到 15px，模型和思考等级按钮溢出到 History 和 Full Access 下面。改动：AI 模式下左组按内容宽度参与换行，放不下时右组换到第二行；终端模式不变，工作目录仍在原位省略。实测 1000px 时两行互不遮挡，1600px 时仍是一行。
- 未写组件测试：jsdom 没有排版，这两处只能用实机测量验证，已在上文记录。

### 8. 侧栏打开会话后的输入焦点（Issue #1）

- 复现：在实机中点击或按 Enter 打开会话后，焦点留在侧栏那一行，打字没有反应；新建会话后焦点留在“+”按钮上。原因正是 Issue #1 怀疑的冒泡：行的处理先把焦点状态设为主面板，点击冒泡到侧栏外层容器后又被设回侧栏，DOM 焦点也从没离开那一行。
- 改动：选中会话、新建会话和打开历史会话后，都发出现成的 `requestTabFocus`，由主面板在页签渲染后把光标放进输入框。手机布局不发，避免一点会话就弹出键盘。
- 回归：选中和新建两种情况，修改前失败；实机复测，点击和 Enter 后焦点都在输入框，输入的文字落在输入框里。

### 9. Issue #1 与实机验收清单

- Issue #1 的勾选状态在 PR 建立后按 hb.3、hb.4 和本阶段证据更新，未完成项链接到本计划。

### 检查结果

- `npm run lint`、`npm run lint:eslint`、`npx prettier --check .`、`npm run lint:doc-refs` 和 `node scripts/hb-release.mjs check` 均通过。
- 全量 `npx vitest run`：2,065 个文件通过、1 个失败、1 个跳过；47,382 项通过、91 项既有跳过、1 项失败。失败的是 `src/__tests__/main/utils/execFile.test.ts` 中“取消时结束继承管道的孙进程”一条：单独重跑三次，两次失败、一次通过。本分支没有改动 `src/main` 或 `src/cli`，这是云容器缺少孤儿进程回收导致的既有不稳定，后端阶段记录过同类现象，主线 CI 在 Linux 和 Windows 上均通过。没有为此跳过测试或放宽断言。

需要在 macOS 上手动核对的项目：

1. **运行中命令输出：** 共享模式下让 Codex 运行一个持续输出的命令（如长测试），在 Maestro 展开该调用：输出应持续出现并跟到底部；上滚后不被拉回；命令结束后状态和最终输出正确。
2. **历史模型信息：** 重新打开一个中途换过模型的 Codex 原生会话，消息信息里应显示各轮自己的模型和思考等级，只在真正换模型的那条回答处提示一次。
3. **未读计数：** 上滚阅读时让智能体运行一个含多次工具调用的回合，计数只随消息和回答增加，回合结束折叠后不变。
4. **窄窗口：** 把窗口缩到最小，手动打开两侧栏：右侧栏的收起按钮、文件工具栏和底部状态栏都应可见；输入框工具栏分两行且互不遮挡。
5. **侧栏焦点：** 在左栏点击或用键盘选中会话并按 Enter，应能直接打字；新建会话同样。
6. **Claude 跨应用刷新：** 终端里用 Claude Code 继续同一会话，Maestro 中可见页签自动追加，阅读位置不动，工具卡原地更新。
7. **既有流程：** 长回合、停止后恢复、共享模式双向刷新、滚动锚点和应用重启后继续，与 hb.4 相同的检查。
