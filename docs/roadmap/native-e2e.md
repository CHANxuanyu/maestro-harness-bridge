# 原生接续端到端验收计划

状态：待 Codex 实施。2026-10-24 起草，用户已确认由 Codex 完成，无需再等审阅。

## 为什么做

[后端改进计划](backend-reliability.md)、[后端第二阶段](backend-followups.md)和[前端第二阶段](frontend-followups.md)都以同一句话收尾：真实应用中的多轮、工具、停止恢复、重启接续、共享双向刷新、跨应用刷新和窄窗口“macOS 实机未验”。现有自动测试停在单元和组件层，没有一条从真实构建的应用一路走到原生转录文件。仓库里已有 Playwright 驱动 Electron 的 `e2e/`，但 CI 不运行它，也没有任何原生接续场景。

本计划要建一套端到端验收：在 CI 里用确定性的假原生程序驱动真实构建的应用，覆盖上述清单；同一套用例在用户的 Mac 上切换到真实 CLI，就是可重复的实机验收工具。

## 工作清单与验收目标

### 0. 让全量测试在云端和 CI 上稳定

- **依据：** 前端第二阶段的全量运行中，`src/__tests__/main/utils/execFile.test.ts` 的“取消时结束继承管道的孙进程”在云容器里时过时不过（三次两败）。后端第二阶段也记录了两个既有的文件时间戳用例在本地失败。
- **做法：** 找到根因再修：是测试依赖了容器没有的孤儿进程回收，还是 `execFile` 的取消逻辑在某些时序下真的漏杀。修测试还是修代码，取决于根因。不跳过、不放宽断言、不加重试。
- **验收：** 这三条在云容器里连续运行 20 次全部通过；CI 两个平台不回退。

### 1. 假原生程序

- **做法：** 放在 `e2e/fixtures/native/`，只用于测试，不进安装包。
  - **假 `claude`：** 接受 Maestro 实际传入的参数（`--print`、`--output-format stream-json`、`--resume <id>`、`--no-session-persistence` 等，以 `src/main/agents/definitions.ts` 和启动路径为准）。按场景脚本输出 stream-json（正文、`tool_use`、`tool_result`、用量、`result`），同时像真实 CLI 一样写 `CLAUDE_CONFIG_DIR/projects/<编码后的项目路径>/<id>.jsonl`。收到 SIGINT 时写入已确认的中断结果后退出；带 `--no-session-persistence` 时不写文件。
  - **假 `codex`：** 接受 `exec --json [resume <id>]` 等参数，输出 exec 事件（`thread.started`、`item.started` / `item.updated` / `item.completed`、`turn.completed`），并写 `CODEX_HOME/sessions/` 下的 rollout 文件（含 `turn_context` 的模型和思考等级）。
  - **共享模式：** 复用并扩展 `scripts/codex-shared/connector.test.cjs` 里的合成 app-server，让应用通过真实的 `scripts/codex-shared` 连接器接入它。
  - **另一端写入者：** 一个辅助脚本，模拟“另一个应用”向同一原生会话追加回合，用于跨应用场景。
- **格式来源：** 所有输出格式只能取自仓库现有的解析器、存储和测试样例，以及锁定版本（`codex-cli 0.163.0-alpha.11.1`，以及已验证的 Claude Code 2.1.310）的官方源码或包。每个假程序在注释里写明来源；不发明字段，不为未知版本加分支。
- **验收：** 每个假程序有自己的单元测试，证明同一脚本输出的事件经仓库现有解析器解析，与它写下的转录经现有存储读取，两者结果一致。

### 2. 端到端测试框架

- **做法：** 扩展 `e2e/fixtures/electron-app.ts`：每个用例使用独立的数据目录、`CLAUDE_CONFIG_DIR`、`CODEX_HOME` 和临时项目目录；用 `maestro-cli create-agent` 等现有命令或智能体的自定义可执行路径接上假程序。界面操作优先使用现有的 role、aria 标签和 `data-*` 属性。
- **前端边界：** 确实没有可用选择器时，只允许在组件上加 `data-testid`，不改结构、样式、文案和行为，并在 PR 中逐条列出。发现前端缺陷时，把复现用例和步骤写进记录交给 Opus，不改前端代码，也不为了通过而放宽断言。
- **验收：** `npm run test:e2e` 在 Linux（xvfb）上可以本地一条命令运行；单个用例失败时保留 trace 和截图，但只放在本地或 CI 工件里，不入库。

### 3. 场景

每个场景都对应前面三份计划里写着“未验”的一项。Claude Code 和 Codex 各跑一遍，适用的才跑。

| 场景          | 要证明的事                                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| a. 多轮       | 同一原生会话连续两轮，界面与转录都追加，原生 ID 不变。                                                                  |
| b. 工具       | 运行中 → 完成，并行工具各自对应；失败与取消显示正确；运行中命令的输出持续更新并跟随到底部。                             |
| c. 停止与恢复 | 工具运行中按 Stop，调用显示为已停止；随后继续发送，仍在同一原生会话；旧错误不清除会话关联。                             |
| d. 重启接续   | 正常退出应用并用同一数据目录重开，会话可打开并继续，原生 ID 不变。                                                      |
| e. 项目历史   | 在应用外预先写好的原生会话出现在项目会话列表；打开后工具卡带结果，消息信息显示原生模型（Codex 另有思考等级）。          |
| f. 跨应用刷新 | 另一端写入者追加回合：页签可见且空闲时自动出现；上滚阅读时位置不动、未读只按消息和回答增加；忙碌页签不刷新。            |
| g. 共享模式   | 经真实连接器接合成 app-server：两端顺序发送；生成中或有队列时拒绝；运行中命令输出增量出现；确认请求的提示出现在对话中。 |
| h. 历史摘要   | 开启“历史记录”完成一轮后，原生转录文件逐字节不变，共享线程没有 Summary 回合，项目列表没有新会话，历史面板有条目。       |
| i. 窄窗口     | 窗口 1000px 且两侧栏打开：右侧栏的收起按钮、文件工具栏和状态栏都在窗口内；输入框工具栏各按钮不相互重叠（比较位置框）。  |
| j. 焦点       | 从左栏点击或按 Enter 打开会话、新建会话后，焦点在输入框，键入内容落入输入框。                                           |

验收：每个场景先在修复前的已知缺陷上证明能失败。可用已经修好的问题做反证，例如临时回退前端第二阶段的窄窗口或焦点修复，确认用例会失败，再恢复；这一步只在本地做，不提交。

### 4. CI

- **做法：** 在 `.github/workflows/ci.yml` 新增一个 Linux 任务，用 xvfb 运行原生接续用例，目标在 15 分钟内完成。CI 中这套用例不使用 Playwright 的自动重试（`retries: 0`），失败即为失败。只在失败时上传 trace 作为 CI 工件。
- **治理边界：** 是否把它加入主线保护的必需检查，属于规则集变更，由用户决定。在 PR 中写明建议，不直接修改 `.github/rulesets/`。
- **验收：** 新任务在 PR 上连续三次推送都通过；原有六项检查不受影响。

### 5. 真实模式（只在本地，需显式开启）

- **做法：** 同一套用例在设置 `MAESTRO_E2E_REAL=1` 时改用本机已安装并登录的 `claude` / `codex`。
  - 始终使用临时项目目录和全新会话，绝不打开、续接或修改用户已有的原生会话。
  - 共享模式只在用户显式提供连接器路径时运行。
  - 运行结束生成一份不含对话内容的摘要（场景、通过与否、CLI 版本、应用提交），供版本验收记录引用。trace 和截图留在本地。
- **文档：** 在 `docs/verification/` 下写明怎么在 Mac 上运行、会消耗多少额度、会在哪里留下临时文件、怎么清理。
- **验收：** 在 Linux 云环境中，用假程序冒充“真实 CLI”走一遍真实模式的启动和清理流程；真实账户下的运行留给用户在 Mac 上做，标记为未验。

## 实施范围

- **分支与 PR：** 分支 `codex/native-e2e`，本计划已在其上。开始前先把最新的 `codex/i18n-zh-cn` 合并进来（前端第二阶段 PR #5 合并后才包含窄窗口和焦点修复）。分三个 PR，目标都是 `codex/i18n-zh-cn`，每个在六项检查通过后由 Codex 合并：
  - PR 1：第 0 项、第 1 项、第 2 项、场景 a 到 e，以及第 4 项的 CI 任务；
  - PR 2：场景 f 到 j；
  - PR 3：第 5 项。
- **可以改的：**
  - `e2e/`、`scripts/` 下的测试工具；
  - `.github/workflows/ci.yml`；
  - `playwright.config.ts`；
  - `package.json` 的测试脚本；
  - 第 0 项涉及的测试或主进程代码；
  - 场景暴露出的后端缺陷（先补能失败的回归再修）。
- **不改的：**
  - 前端界面（`data-testid` 例外，见第 2 项）；
  - 认证、订阅、原生写锁和进程终止方式的产品行为（第 0 项确认是代码缺陷时除外）；
  - 依赖升级：不升级依赖，不新增运行时依赖；测试依赖只用已有的 `@playwright/test`。
- **不发布、不打包、不安装。**

## 特殊要求

沿用[后端改进计划的特殊要求](backend-reliability.md#特殊要求)七条：拒绝过度防御、不新增哈希或校验体系、不混入既有哈希机制的清理、最小修改、错误如实传递、测试验证行为、限制改动与证据量。另外：

1. **假程序的边界：** 只模拟仓库已经支持的行为，不为测试方便在产品代码里加旁路，也不加“测试模式”分支。
2. **用例写法：** 用例断言用户可见的结果和原生文件的实际字节，不断言内部实现细节。
3. **不入库的内容：** 截图、trace、真实模式的输出和任何对话内容都不入库。
4. **检查要求：** 推送前运行 `npm run lint`、`npm run lint:eslint`、`npm run format:check:all`、相关 Vitest 和新的端到端用例。
5. **写作风格：** 新写的文档、注释和提交说明不使用长破折号或短破折号（见 `CLAUDE.md`）。
