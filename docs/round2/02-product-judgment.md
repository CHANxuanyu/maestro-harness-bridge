# 第二轮：产品判断

依据见 [01-evidence.md](01-evidence.md)。可操作的方案见 [原型](prototype/index.html)。

这份文件是 11 月 14 日的判断过程，写于评审之前。范围、行为和规则的权威版本在 [PRD.md](PRD.md)，验证结果在 [03-verification.md](03-verification.md)，评审之后的修订见 [06-review-response.md](06-review-response.md)。下面有四处已经被修订，以 PRD 为准：第 3 节里"默认不开会"和"用决定权规则代替共识比例"的说法；第 5.1 节"先做单聊的能力，再做团队"的排序；第 5.3 节里对旧群聊的说法；凡是把团队写成"可选"的地方。

## 1. 一句话

第一轮把壳换成了 Claude Code 的样子。第二轮要做两件事：**让结果而不是过程成为界面的主体**，以及**让几家模型像一个有纪律的小团队那样把一件事做完，而不是像一个聊天群那样把一件事聊完**。

## 2. 我对问题的判断

### 2.1 日常界面：问题不在状态栏，在信息的排位

你说注意力被工具状态栏吸走。实测后我的结论是，状态栏只是最显眼的那一个，根因有三层：

1. **运行中，界面上唯一在长的东西是工具日志。** 人的眼睛会跟着动的东西走。助手说的"我在做什么、为什么"反而不显示，真正有信息量的计划进度藏在右栏的一个标签页里。
2. **同一个"在运行"被画了五遍。** 左栏、顶栏、工具行、底部计时、发送键。五处同时在动，其中一处每秒跳一次。
3. **颜色在说谎。** 先写一个会失败的测试是正确做法，界面却给它标红，回合成功后红字还留着。红色用多了，真出事的时候就不显眼了。

所以方案的原则是一条：**注意力按"这条信息会不会改变你下一步的动作"来分配。**

运行中你只想知道四件事：还在动吗；它在干什么；需要我吗；大概到哪了。工具调用一条也回答不了，它是审计证据，应该点开才看。

完成后你想知道的是：结果是什么；改了什么；验证过吗；还剩什么。所以回合末尾应该是交付信息，不是工具统计。

### 2.2 团队协作：卖点成立，但成立的不是"群聊"

> 11 月 17 日补充：这一节写于评审之前。团队群聊现在是第二轮必须交付的核心功能，协作方式也按评审意见改过：讨论保留并且是真讨论，范围内的事由团队自己定，PM 对产品效果把关。现行的设计在 PRD 第 6 节，改了什么见 06。

你设想的画面是一个群：老板丢想法，PM、开发、QA 在里面讨论、对齐、推进。我认同这个目标，但认为把它实现成聊天群会失败，原因有四个，都来自 agent 和人的差别：

1. **agent 不会"等"。** 人说"等 CI"之后会自己回来看；agent 的回合一结束，什么都不会发生，除非有东西去叫醒它。现有群聊正是这样停住的：唯一的触发是"所有人都回复了"。所以"自主跟进"不能靠给主持人写更长的提示词，只能靠应用里一个不会忘事的调度器。
2. **agent 之间的共识很便宜。** 模型倾向于附和，同一家的模型有相同的盲区。三个 agent 里两个同意，可能只相当于一个半独立意见。把它当作决策依据，会放大错误而不是纠正错误。
3. **"我做完了"不可信。** 需要的是测试结果、改动、复现步骤这些东西，而且要由应用或者另一个岗位来确认。
4. **三个 agent 的流水账比一个 agent 的工具日志更吵。** 如果团队界面就是把三份输出混在一起，那等于把 2.1 的问题放大三倍。

所以我的方案里，团队的核心不是聊天，是三样东西：

- **台账**：需求、决定、工作项、问题、证据。它是持久的、共享的，也是换人和重启后还能接着干的原因。
- **调度器**：应用里的一段确定性逻辑，负责在回合结束、检查结束、到点、出错、重启时决定下一步叫醒谁。
- **团队对话**：给你看的界面。长得像群聊，但讨论会折叠成一条带结论的讨论串，决定、问题、演示是卡片，需要你的事置顶。

多家工具在这里是真正的优势，而且是原生工具给不了的：Claude Code 的 agent teams 和 Codex 的多 agent 都只能在自家模型里组队，状态也不跨会话恢复。**让不同厂商的模型互相检查、额度用完换一家接着干、应用重启后原地继续**，这三件事只有我们这个位置能做。

## 5. 推荐方向与取舍

### 5.1 先把"跟进"和"验收清单"做成单条对话的能力，再用它们搭团队

团队功能里风险最大的两块是：应用能不能可靠地在事后叫醒一条对话；应用能不能自己跑检查并把结果当证据。这两块完全可以先在单条对话上做出来、每天用、验证可靠，然后团队只是把它们和台账组合起来。

好处：日常马上受益；团队功能的地基在上线前就被真实使用过；如果团队形态最后需要调整，这两块不会白做。

代价：团队功能晚一个阶段出现。我认为值得。如果你希望更早看到团队，备选是 R2.2 和 R2.3 并行，但那样地基没有经过日常使用就被建了上层。

### 5.2 团队 v1 只做一个开发岗位

多个开发并行需要 worktree 之间的合并和冲突处理，这是另一个量级的问题。v1 是 PM、一个开发、一个 QA，同时最多两个岗位在跑。先证明一个完整循环不用催就能走完。

### 5.3 不恢复旧群聊界面

旧群聊是"主持人模型即调度器"的设计，停住、转述失真、重启丢状态都源于此。团队功能在新界面的子任务树上重建，复用群聊的底层部件。

### 5.4 这一轮不做的

- 人格化的专家市场（WorkBuddy 的路子）。岗位是职责和权限，不是人设。
- 云端托管、关机后继续跑（WorkBuddy、Cursor 的路子）。先保证本机重启能恢复。
- 多人共用一个团队任务（Cursor 的 multiplayer）。
- 多个开发并行。
- 语音、移动端的团队视图。

## 6. 细节上的具体判断

你要求不能只说"更现代、更丝滑"。以下每条都能在原型里看到或在验收标准里量到。

| 方面       | 判断                                                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 键盘       | 模型选择器：⌥⌘. 打开，焦点在筛选框；上下选模型，右或 Tab 到强度列，Enter 确定，Esc 关闭并把焦点还给输入框。全程不碰鼠标 7 次按键内可以同时换模型和强度 |
| 焦点       | 弹出层打开时拿走焦点，关闭时还回触发它的控件。弹出层开着时 Esc 只关弹出层，绝不传到"停止回合"                                                          |
| 弹出层     | 高度按可用空间算，不裁切。强度列属于正在高亮的模型，高亮哪个就显示哪个的档位                                                                           |
| 留白与对齐 | 对话列最宽 760，用户气泡靠右、最宽占 82%，助手内容和活动条左对齐成一条线                                                                               |
| 字体       | 等宽字只用在命令、路径、标识本身。动词、标签、状态用界面字体。步骤明细比正文小一号、暗一级                                                             |
| 动画       | 一条对话里同时最多一个在动的元素。计时不逐秒跳：前 10 秒"刚开始"，之后按 10 秒、再按分钟。弹出层 150 毫秒以内                                          |
| 颜色       | 强调色只给"需要你"。红色只给回合级的失败。预期内的失败在明细里用中性文字写明                                                                           |
| 长列表     | 模型列表默认只列主要模型，较早的收在"更多模型"里。左栏沿用"显示更多"                                                                                   |
| 滚动       | 活动条高度不变，所以运行中不推动你正在读的内容。只有你本来就在底部时才跟随新输出                                                                       |
| 通知       | 你正看着的对话完成时不亮铃铛。"需要你"在左栏用实心点，和"运行中"的转圈分开                                                                             |
| 响应速度   | 目标写在路线图的验收标准里，都是相对现有实测基线的，不编造数字                                                                                         |
