## 3. 真实模型配合团队机制

### 3.1 做了什么

一个脚本调度器按 PRD 的流程驱动三个真实岗位：PM 写需求，开发和 QA 同时各写一份互相看不到的意见，PM 回应，模拟老板确认基线，开发在自己的 worktree 实现，脚本运行检查，QA 在自己的 worktree 写测试并验证，问题进入修复和复验，PM 演示。"老板"只做两件事：确认基线，最后看演示。全程不发任何消息。

- 模型：Claude Sonnet（Effort Low）和 Codex GPT-6.1-Sol（Reasoning Low）。用低强度是为了省额度，也是更苛刻的条件。
- 任务：给一个小库写时长解析函数。想法故意写得不合理："支持所有常见写法，绝对不能出错"。
- 会话都不落盘，不进你的原生历史。
- 岗位用回合结尾的 `team-report` 代码块报告，脚本解析。
- 脚本有两版：`私有证据 teamlab/sched.mjs`（运行 1 到 3）和按前三次的发现改进规则后的 `sched2.mjs`（运行 4）。

### 3.3 看到了什么

**成立的部分（实测）**

- 不催也能走完。四次都从想法走到演示，没有一次停在"等一下"。
- 报告块可靠。39 个回合全部一次交出能解析、通过校验的报告，补报一次都没用上。
- PM 会把不合理的想法收窄成可验的标准，并写明不做什么。
- 独立写意见有用。运行 1 里开发和 QA 互相看不到，却各自指出了同一处笔误和同一处错误类型不一致。
- "成员说完成"不等于完成。运行 1 里开发第一次报告完成时，脚本运行检查发现连测试文件都没有。
- QA 能抓到真问题。运行 3 和运行 4 里，QA 都在第一次验证就发现了植入的错误，给出能直接运行的复现命令；开发一次修好；QA 复验通过。
- 隔离守得住。QA 只写了 `qa/`。
- 演示如实。运行 3 的演示把两条没达成的标准标成未通过，建议继续，并列出了没验证的部分。

**前三次暴露的缺口（实测）**

1. **检查命令本身可能在这台机器上跑不起来，而开工前没有人发现。** `node --test qa/` 这条命令是我的脚本规定的（相当于产品里"应用要运行的检查"），PM 把它抄进了基线。它在本机的 Node 24 下直接报找不到模块。三次运行都撞上了：运行 1 和运行 2 的 QA 在自己的目录里加了一个入口文件绕过去，运行 3 的 QA 认为不该绕，上报等裁定。
2. **标准本身有问题时，流程里没有路。** 运行 3 的基线里，一条示例和另一条规则互相矛盾。质询阶段没人发现，QA 在验证时发现了。开发和 QA 都正确地说"需要裁定"，但脚本只会再派一轮修复、再叫一轮复验，空转了 4 个回合，占那次用量的 31%。
3. **质询可以被敷衍。** 运行 2 里 QA 的质询回合用 8 秒交了一份空意见。

这三条都是流程的洞，不是模型的错。流程上的洞要靠应用的规则补，靠提示词补不了。

**改进规则后重跑（运行 4，实测）**

改了四处：确认基线前试跑检查命令（PRD R1 第 2 条）；QA 的质询产出改成逐条的验证计划（R2 第 3 条）；标准问题交给 PM 而不是开发（R1 第 10 条）；开发说没有可修的就不叫 QA 复验（R2 第 7 条）。

| 改动                          | 运行 4 里发生了什么                                                                       |
| ----------------------------- | ----------------------------------------------------------------------------------------- |
| 试跑检查命令                  | 作为对照，把前三次那条命令交给试跑：被拦下。PM 这次自己写的两条命令试跑通过，之后全程能用 |
| QA 交验证计划                 | 9 条标准全部有计划，另提了 6 条异议。没有再出现空意见                                     |
| 同样的植入错误                | 一轮修好并复验。总共 9 个回合、48 万输入 token，是运行 3 的 45%                           |
| 标准问题走 PM、没改动就不复验 | **没有被触发**：这次 QA 没有报告标准问题。这两条路径仍然没有真实模型的运行数据            |

所以能说的是：试跑和验证计划这两条有了运行结果；空转消失了，但消失的直接原因是这次没有出现标准问题，另外两条规则的效果还没有被检验。

### 3.6 团队和单条对话对比

这是一个小任务上的一次对照。它能说明的事情有限，先把结论放在前面：**它只说明小任务不必用团队，不能用来判断团队群聊值不值得做。**

**做法**

- 同一个想法、同一个空项目，另外跑两条"单条对话"：一条由 Codex 直接做完，一条由 Claude 直接做完。每条再让另一家只读复核一次、原作者修一次，对应产品里已有的"让另一家复核"。
- 一把中立的尺子（`私有证据 teamlab/rubric.mjs`）：48 个输入，分两档。第一档 28 个是想法里点名的那类写法（`90s`、`1h30m`、`2 天`、`1.5h`、空串应报错等）。第二档 20 个是不那么显眼但没有歧义的写法（`1 hour 30 minutes`、`0.5d`、`2个小时`、`1.2.3h` 应报错等）。尺子在看到任何单条对话的结果之前写定，没有看任何一份实现的代码。

**结果（实测，每种只跑了一次）**

| 做法                               | 第一档 | 第二档 | 回合 | 用时   | 输入 token |
| ---------------------------------- | ------ | ------ | ---- | ------ | ---------- |
| Claude 单条对话                    | 28/28  | 20/20  | 1    | 51 秒  | 9 万       |
| Codex 单条对话                     | 28/28  | 19/20  | 1    | 108 秒 | 12 万      |
| Codex 单条对话，加 Claude 复核一次 | 28/28  | 20/20  | 3    | 256 秒 | 30 万      |
| Claude 单条对话，加 Codex 复核一次 | 28/28  | 20/20  | 3    | 227 秒 | 51 万      |
| 团队，运行 1                       | 28/28  | 19/20  | 8    | 271 秒 | 43 万      |
| 团队，运行 2                       | 28/28  | 19/20  | 9    | 354 秒 | 51 万      |
| 团队，运行 3                       | 28/28  | 19/20  | 13   | 445 秒 | 106 万     |
| 团队，运行 4                       | 27/28  | 16/20  | 9    | 272 秒 | 48 万      |

**怎么读**

1. **在这个小任务上，单条对话更省。** 它一回合就拿到了和团队同样或更高的分数，用量是团队的五分之一左右，用时是三分之一左右。这类任务模型一回合就能做对，团队的长处没有用武之地。
2. **团队的结果被基线框住。** 运行 4 丢的分全部来自同一个决定：PM 把小数写法（`1.5h`）划到了"不做"里。脚本里的老板没有看就确认了基线，团队于是严格交付了一个更窄的东西。这不是执行出错，是范围决定。它说明确认基线是一次真决定，卡片必须把"不做什么"摆在显眼处（PRD R1 第 1 条）。
3. **"另一家复核一次"是有效且便宜的中间档。** Codex 那条从 19/20 到 20/20，代价是多两回合。这个能力产品里已经有了。

**这组数据不能说明什么**

- 只有一个任务，而且是模型一回合就能做对的那种小任务。中等以上、要跨多个文件、要求不清楚的任务上会怎样，没有数据。
- 每种做法只跑一次。尺子是我写的，虽然写在结果之前。
- 没有测"单条对话遇到植入错误时，复核能不能抓到"。

**为什么不能据此判断团队值不值**：只有一个任务，而且很小；每种做法只跑一次；团队那几次有的被植入了缺陷，单条对话没有，条件不一致；运行 4 的分数还受 PM 缩窄范围的影响。

**对方案的含义**：新建团队时，对很短的想法给一句"一条对话可能就够了"的提示。团队群聊是必须交付的核心功能，不受这组数据影响。条件一致的中等任务对照排在 [04-roadmap.md](04-roadmap.md) 的第 4 节，用来确定适用场景和默认配置。

## 5. 日常界面的两个缺口

### 5.1 菜单开着按 Esc

**实测**（试用包，合成 provider，35 秒的长回合运行中，用鼠标打开模型菜单）：

| 按 Esc 时焦点在哪                  | 菜单 | 回合                                        |
| ---------------------------------- | ---- | ------------------------------------------- |
| 菜单按钮上（鼠标点开后的默认状态） | 没关 | 继续运行                                    |
| 输入框里                           | 没关 | **被停掉**（停止键消失，provider 进程结束） |

第二种状态我是用脚本把焦点移回输入框造出来的，日常里出现的频率没有数据。结论：Esc 关不掉菜单是确定的；菜单开着时 Esc 能越过它停掉回合，这条路径存在。D9 的规则"弹出层开着时 Esc 只关弹出层"有了实测依据。截图在 `私有证据 maestro/09` 和 `12`。

### 5.2 Codex 回合里的过程说明

**实测**（真实 Codex，GPT-6.1-Sol，试用包，一个改 bug 加测试的回合，29 秒）：

- 事件流里有过程说明：回合开头、第一个工具调用之前有一句"我会先检查…"。
- 运行中，主视图只有一行"Thinking… · 6s"。
- 完成后，主视图是折叠的"Worked for 29s"加最终答复。那句过程说明不在主视图里。
- 顺带看到：左栏的对话标题变成了那句过程说明，还带着反引号；顶栏仍是用户消息原文。两处标题不同源，标题带 markdown 记号，正是 D6 要修的。

截图在 `私有证据 maestro/10` 和 `11`。这个研究实例当时是旧界面布局；对话区的呈现组件两种界面共用（代码），新界面上的同类截图见 01 的第 2 节（合成 provider）。

### 6.1 任务面板失败的原因（已查清并复现）

**更正**：我上一版写的是"Claude 一半失败"。那是看错了报错位置。两次失败都发生在 **Codex 那一半**，Claude 那一半两次都没有跑到。

**现象**：真实 Codex 回合正常结束，应用右侧"任务"页正确显示了两条任务和"1 / 2 completed"。然后场景去 Codex 的原生记录里找一条名叫 `update_plan` 的函数调用，用它作为独立的对照，找到 0 条，断言失败。

**原因（实测，单独复现）**：在 Codex 0.169 上，模型不是直接调用 `update_plan`，而是通过"代码模式"：原生记录里是一条名叫 `exec` 的自定义工具调用，输入是一段脚本 `text(await tools.update_plan({...}))`。运行时的事件流里另有一条 `todo_list`，应用读的是它，所以界面是对的。原样的记录行在 `私有证据 real-acceptance/codex-plan-call-rollout-rows.json`。

也就是说：这是 CLI 版本漂移造成的，场景按 0.163 的记录形状写，0.169 换了形状。场景配置里写了关闭代码模式，在 0.169 上没有生效，还带出两条"配置项已弃用"的报错。

查的过程里排除掉的原因：不是模型没调用（界面上有清单）；不是只读模式；不是我选的 Claude 模型（没跑到那里）。

### 6.2 由此发现的一个产品缺陷：Codex 的计划重启后会丢

- **实测**：0.169 的原生记录里，计划只存在于那条 `exec` 脚本里，没有别的行记录它。
- **代码**：产品从原生记录重建历史时，把这条调用当成一个名叫 `exec`、输入是纯文本的工具调用，不会从脚本里取出计划。
- **推断**（确定性很高，但没有在应用里重启验证，因为场景在这一步之前就失败了）：对话运行时任务页是对的；重启应用之后，或者从原生历史重新打开这条对话时，Codex 的任务清单消失。

你日常用的 Codex 会话记录里（0.166）已经是这种形状，所以这不是将来的问题。

### 6.3 Claude 这一侧：任务清单大多数时候根本没有数据

顺着查下去的结果，全部**实测**（`私有证据 real-acceptance/claude-task-tools-by-model.txt`）：

| 模型                           | Claude Code 默认提供的任务清单工具              | 设了 `CLAUDE_CODE_ENABLE_TASKS=false` 之后 |
| ------------------------------ | ----------------------------------------------- | ------------------------------------------ |
| Haiku 4.5、Sonnet 4.6          | `TaskCreate`、`TaskUpdate` 等，一条任务一次调用 | `TodoWrite`                                |
| Sonnet 5、Sonnet 5.5、Opus 5.5 | **没有**                                        | **没有**                                   |

- 5 系模型在任何权限模式、两个 CLI 版本（2.1.291 和 2.1.317）下都没有任务清单工具。让它调用时，它如实回答"这个工具不可用"。
- 4 系模型默认用的是 `TaskCreate` 那一组。产品的解析只认"一次调用里带一个任务数组"的形状（**代码**），所以认不出来。只有设了那个开关才会出现产品认识的 `TodoWrite`，而设这个开关的只有验收场景自己，产品正常启动 Claude 时不设（**代码**）。

合起来：**今天的产品里，Claude 对话的"任务"页在真实使用中基本不会有内容。** 5 系没有来源，4 系的来源产品不认识。即使把 6.1 的问题修好，这个验收场景的 Claude 一半用 5 系模型也必然失败，用 4 系能过只是因为场景自己设了开关，不代表真实使用。

没有测：Fable 系模型（推断同 5 系）；交互式 TUI 下的情况。

## 7. 竞品的缺口

### 7.1 Cursor

**没有上手。** 检查过的：`/Applications` 和 `~/Applications` 里没有 Cursor，没有 `~/.cursor`，没有 `cursor` 命令。它的团队形态（Projects）需要带 Cloud Agents 的付费计划。安装、注册、付费都需要你本人，所以停在这里。

**官方资料**里和我们相关的几点：

- 协调者自己不写代码，只指挥别的 agent；它做计划，然后派 agent 并行地实现和测试各个部分。
- 有任务看板（列表或看板视图），常见的分栏是待审、进行中、排队、完成、取消；工作 agent 对看板只读。
- 需要人的时候有"Input Needed"标记。人审的是 PR。没有正式的"计划确认"关卡。
- 官方建议：agent 不应该自己合并或部署；一个工作 agent 被纠正超过两次就停掉重来。

和我们的差别（**推断**）：它的岗位都在自家模型和云端；它没有"基线"这种人确认的验收标准，也没有"修的人不验"。

### 7.2 WorkBuddy

- **实测**：单专家对话、专家列表、召唤团队的入口，直到弹出"确认消耗更多积分"为止。我没有替你勾选，点了取消。没有产生任何任务或消耗。
- **官方资料**："专家团由多位专家分工协作，由团长自动拆解、并行执行并整合交付。"积分消耗通常是单专家的 3 到 5 倍，以实际任务为准（转述）。文档没有描述阶段划分、每个成员的进度怎么显示、中途怎么干预。
- **没有看到**：团队运行中的界面。

排除 HY 自有模型优势的做法没有变：只比较产品形态和交互，不比较模型输出质量。

### 7.3 这两处缺口影响什么

不影响 PRD 的任何一条规则，它们都不是从这两个产品推出来的。影响的是竞品对比里"用起来怎样"的那一栏，那一栏对 Cursor 和 WorkBuddy 的团队模式目前是空的。
