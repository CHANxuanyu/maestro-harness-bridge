## 1. 背景与目标

### 1.1 要解决的问题

1. **日常对话里，过程盖过了结果。** 运行中界面上唯一在增长的是工具日志，同一个"在运行"画了五处，助手说的"为什么"不显示，预期内的失败被永久标红。证据见 01 的第 2 节。
2. **模型和强度的选择器丢掉了厂商给的信息。** 两家都在本机提供带名字、说明、每个模型档位表和默认档的目录，现在只用了模型标识，强度档位是所有模型的并集。证据见 01 的第 4 节。
3. **"几家模型一起把一件事做完"还不存在。** 旧群聊在新界面里没有入口；实际运行时，主持人说"等 CI"之后什么都不会发生，成员额度出错不留痕迹，强制退出后进行中的派发丢失，主持人一个角色用掉 86% 的输入。实测见 03 的第 2 节。
4. **"做完了"没有证据。** 单条对话和团队都一样：助手说完成就是完成，没有任何东西由应用确认。

### 1.2 产品目标

| 编号 | 目标                                                                   | 怎么算达到                                                                                                                               |
| ---- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| G1   | 日常对话里，注意力落在"需要我吗、做到哪了、结果是什么"                 | 运行中对话区只有一个高度不变的活动条；一条对话里同时在动的元素只有一个；成功的回合不带错误色                                             |
| G2   | 选模型和强度时，看到的就是厂商自己的说法，按模型                       | 名字、说明、档位、默认档全部来自厂商目录；界面上不出现厂商没用过的档位译名                                                               |
| G3   | 一条对话说"等一下再回来"，它真的会回来；说"做完了"，有应用跑出来的证据 | 跟进由应用持有并落盘，重启后仍触发；检查由应用运行，结果不取自助手的文字                                                                 |
| G4   | 团队群聊：老板提出想法、选好模型和岗位，团队自己把它做到可验收         | 从提出到验收，老板只做真正归他的决定，不发任何"继续""进度如何"；等待超时、检查失败、额度用尽、重启之后团队自己接着走                     |
| G5   | 团队会自己想、自己谈、自己定，并且有人对产品效果负责                   | 范围和预算内的分歧由团队讨论后自己定，留下结论和保留意见；检查全过时 PM 仍会对着真实产出把关，不合格就打回；老板不是唯一发现体验问题的人 |

### 1.3 不做的事

- 人格化的专家市场。岗位是职责和权限，不是人设。
- 云端托管、关机后继续运行。
- 多人共用一个团队。
- 多个开发岗位并行（需要 worktree 之间的合并协调，放到 v1 之后）。
- 检测官方 CLI 更新并自动适配。按老板的要求留到以后讨论。
- 照搬旧群聊的实现。团队群聊在新界面里重建，复用旧群聊的底层部件，见第 7 节。

## 3. 范围总览

三个模块，按依赖顺序排列。编号在所有文件和原型里通用。

| 模块             | 内容                                                                             | 编号      | 原型场景   |
| ---------------- | -------------------------------------------------------------------------------- | --------- | ---------- |
| A 日常对话       | 活动条、状态只画一处、失败语义、交付条、左栏、模型与强度选择器、任务清单如实显示 | D1 至 D12 | 日常对话   |
| B 跟进与验收清单 | 单条对话的"稍后回来"和"应用跑检查"                                               | F1 至 F6  | 跟进与验收 |
| C 团队群聊       | PM、一个开发、一个 QA；讨论与决定、PM 产品评审、台账、调度器、团队主视图         | T1 至 T20 | 团队群聊   |

B 是 C 的地基：团队里的"等 CI 不停住"就是 B 的跟进，团队里的"检查通过"就是 B 的检查运行器。两个模块共用的规则（授权、等待、进展、恢复、终态）写在 3.1，模块里只写各自的默认值。

**模块 C 是第二轮必须交付的核心功能，不因任何对照结果而取消或缩成"一条对话加 QA"。** 对照实验保留，用来研究适用场景、岗位配置、讨论机制、质量和成本，见 [04-roadmap.md](04-roadmap.md) 的第 4 节。团队不是每次新建的默认入口，但入口要清楚、好找。B 和 C 共用的基础能力（跟进、检查运行、往对话里派发）在同一段里做，尽早跑通一条最小的完整团队流程，不等单聊的所有界面都做完。

### 3.1 共用规则：授权、等待、进展、恢复、终态

单条对话和团队群聊用同一套原则，下面每条在两个模块里都适用，模块里只写各自的默认值和差别。原则是：**在授权和预算之内，系统自己想办法往前走；局部次数到了是换打法的信号，不是把问题交给老板的信号；防的是没有新证据的相同尝试，不是某一类办法用了几次；只有下一步必须追加预算、改变承诺、提供登录或新权限时，才找老板，而且给的是具体选项。**

每条后面标了现在的状态：**原型已验证**指原型 P7.1 里能实际操作并有自动检查；**规则已定义**指写清了但原型里没有画；所有条目的**真实可靠性都要到开发阶段验收**，原型不能代替。

#### 3.1.1 一次授权，同一范围内不再问（原型已验证）

- 授权按范围记住，不按命令。单条对话的范围是"这个项目"，团队的范围是"这个团队"。
- 范围内的动作直接做：在项目或任务工作区里运行检查命令（命令改了也一样），在任务分支上提交和推送，开草稿 PR，用已授权的替补或团队已选用的模型接任。哪些在范围内，是老板授权时勾选的。
- 超出范围的动作单独问，而且问得具体：说清是哪个动作、超出了哪一条边界、不做会怎样。例如检查命令要下载到项目之外或联网写入；推送到任务分支之外；用一个这条对话或这个团队没授权过的模型。
- 只问一次。同意之后，同一范围内的同类动作不再问；"只允许这一次"的不扩大授权。
- 始终要老板确认：合并、发布、对外消息、放宽或删除已确认的标准、追加时间或预算、新的付费模型。

#### 3.1.2 三种限度，分开定义（原型已验证）

| 限度         | 管什么                                         | 单条对话的默认值                  | 团队的默认值                    | 到了之后                                                                                                   |
| ------------ | ---------------------------------------------- | --------------------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 单次等待时限 | 登记的一次等待：等 CI、等一条命令、等额度恢复  | 20 分钟                           | 20 分钟                         | 叫醒登记的一方，附上那件事的当前状态。还在正常进行就接着跟，改成较低频率；状态说明出了问题就诊断。不找老板 |
| 局部尝试次数 | 同一个问题上的连续无进展（重复的尝试也计一次） | 3 次                              | 3 次                            | 诊断，换一个有新依据的方案（3.1.4）。不找老板                                                              |
| 整体预算     | 这件事最多花多少时间和回合                     | 总时限 2 小时，自动修复和跟进共用 | 截止时间（可不设）和回合预算 40 | 硬边界。停下来写未完成报告，由老板决定追加、接受遗留项或停止                                               |

- 整体预算一开始就显示：单条对话在老板选"发回去继续修"时写明"自动修复和之后的跟进共用一个总时限，默认 2 小时"，尝试记录上一直显示已用多少；登记跟进时卡片上写"总时限 2 小时，最迟到 16:20，到期时最后看一次、写下现状、停止并告诉你"，可以当场调整。团队在建队对话框里设，团队顶部一直显示已用多少。
- 整体预算不会悄悄延长，也不会悄悄放弃：到了就停，并说清现状。
- 预算用到 80% 时，团队的 PM 出一个收尾计划（先保哪几条标准），单条对话不需要。

#### 3.1.3 什么算有效进展（原型已验证）

进展只看应用能观察到的证据，不看成员怎么说。

| 算有进展                                                                     | 不算有进展                                                 |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 失败的检查或未满足的标准变少了                                               | 改了代码，但检查结果和上一次完全相同                       |
| 失败的报错变了，而且之前出现过的报错没有回来                                 | 回到了之前出现过的报错                                     |
| 拿到了能缩小原因的新证据：复现出来了、定位到具体文件、做了一个有结论的小实验 | 只改了台账里的文字、重述了计划、换了一种说法描述同一个结论 |
| 产品评审里，上一轮的具体问题有一条以上经 QA 核对已解决                       | 评审意见原样重复                                           |

**等待不是失败。** 正常等待包括：CI 在排队或运行、外部任务在执行、额度按约定时间恢复。等待期间每次查看结果没变，不计入"无进展"，也不触发诊断。只有外部状态本身说明出了问题（被取消、报错、找不到执行它的机器），或者到了单次等待时限再看一眼时状态异常，才进入诊断；只有到了整体预算才停。

#### 3.1.4 没有进展时：不重复，先诊断，再换方案（原型已验证）

要防的是**同一个问题上、没有新证据的相同尝试反复执行**，不是限制"定位""小实验""换做法"这些类别的使用次数。

1. **每次尝试先写三样**：依据（基于哪条证据或哪个假设）；和此前尝试的区别；预期验证什么（做完应该看到什么）。应用把它记进这个问题的尝试记录，连同这次实际的改动或实验内容（用来比对），以及做完之后应用跑出来的结果。
2. **同一类别可以多次使用。** 两次定位查的是不同的假设，两次小实验验证的是不同的方案，就是两次不同的尝试。类别只做记录，不参与"能不能继续"的判断。
3. **重复的尝试不算新办法。** 判断看内容，不看说法：实际的改动或实验和此前某一次相同，而且那次之后没有拿到任何新证据，就是重复。只换了名字或措辞的重复同样按重复记，计一次无进展，应用不会把它当作下一步再派发。
4. **有进展就更新问题状态，接着推进。** 找到原因、拿到新证据、解决了一部分（比如旧报错消失、出现了新的问题），按 3.1.3 都算有进展：应用更新问题状态（未定位、已定位原因、部分解决、已解决）和尝试记录，无进展计数清零。新冒出来的问题单独记，有自己的计数。
5. **连续 3 次无进展，先诊断。** 诊断写出：为什么前几次没用；下一步依据什么；和之前有什么不同；预期看到什么变化。单条对话由助手做，团队由 PM 主持复盘。诊断之后计数清零；之后再连续 3 次无进展，就再诊断一次，每次都要有新的依据。
6. **授权内暂时想不出有依据的下一步，先补证据**（复现、定位、做小实验），不升级。补证据同样受"不重复"和整体预算约束。查明缺的是授权外的东西（新权限、新模型、本人登录、需要老板澄清或改变的承诺），才按 3.1.5 升级，并写明缺的是哪一样。
7. **"还没全部通过"不等于"没有进展"，更不等于"授权内的路走完了"。** 只要整体预算还有、授权内还有有依据的下一步，就继续。
8. **"换个更强的模型可能做得更好"只能是建议**，记在尝试记录里，不能单独成为停下来找老板的理由。只有证据表明现有模型做不到（比如缺少这件事必需的能力），换模型才是一条要授权的路。

不会做的事：重复执行没有新证据的相同尝试；无限次重试（整体预算是硬边界）；未经授权换模型或用新的付费模型；按类别用了几次来宣布"办法用完"。

#### 3.1.5 什么时候找老板，给什么（原型已验证）

只有下一步必须越过一条边界时才找老板。边界是这几种：

| 边界               | 例子                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 整体预算或截止时间 | 单条对话的总时限到了；团队到了截止时间或回合预算。写未完成报告（3.1.2）                                                                       |
| 改变承诺           | 缩小范围、放宽或删除已确认的标准、改证明方式；标准的含义只有老板能澄清时也归这一类。例如为了让检查通过而打开 `skipLibCheck`，等于放宽类型检查 |
| 新权限             | 授权范围外的动作，例如检查命令要联网写入、推送到任务分支以外                                                                                  |
| 新模型             | 用一个这条对话或这个团队没授权过的模型，或者新的付费模型                                                                                      |
| 本人登录           | 只有老板能完成的登录或凭据，例如公司私有源的登录过期                                                                                          |

团队另有三个本来就归老板的节点：确认基线、会改变交付形态的分歧、演示验收（6.4、6.6）。它们是流程里的固定节点，不是升级。

升级卡片必须包含：

- **具体卡在哪**：要越过的是哪条边界，为什么。例如"安装 2.3 要登录公司的私有 npm 源，返回 401"；
- **为什么授权内没有路了**：授权内每条有依据的路分别试到了哪一步、结论是什么；
- **两到三个具体选项**，每个写明代价，以及选了之后谁做什么；
- **推荐哪一个**，为什么；
- **已用的预算**，以及老板决定之前系统做什么：停止这件事上的尝试；单条对话的总时限暂停计时；团队的截止时间不变（它是老板定的时间点），等待不消耗回合预算，不依赖这件事的工作照常。

卡片上不出现"继续"这类不说明做什么的按钮，也不能用"几类办法都试过了"代替上面这些说明。

#### 3.1.6 终态必须如实（原型已验证）

一件事结束时只有三种终态，界面、台账、统计都按这三种区分：

| 终态                    | 什么时候                                             | 顶部显示                                          | 台账里保留什么                                                                 |
| ----------------------- | ---------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------ |
| 已验收：全部达标        | 所有已确认的标准都有证据，PM 评审通过，老板验收      | "已验收：全部达标"                                | 全部证据                                                                       |
| 已验收，接受了 N 项遗留 | 到了整体预算，老板在未完成报告上选了"接受这些遗留项" | "已验收，接受了 N 项遗留"，"在解决"一栏列出遗留项 | 每条遗留项仍标为未达标；证据缺口；老板接受的具体范围；后续清单里的条目和负责人 |
| 已停止：未完成          | 老板选了停止                                         | "已停止：未完成"                                  | 没有完成的标准；分支和台账保留                                                 |

另外有一个非终态：**未完成，等你决定**，就是未完成报告摆在老板面前的时候。未完成报告不是完成演示，卡片上写明"这是进度报告，不是完成演示"。

统计（老板做了几次决定、讨论几次、打回几次、复盘几次、恢复几次、用了多少回合）全部从实际走过的路径计算，不写固定数字。

## 4. 模块 A：日常对话

### 4.1 需求

#### 4.1.2 档位由实际接入方式决定

Maestro 用各家的命令行接入，能选的档位以接入方式实际接受的为准，不凭档位名字猜能力。

| 工具        | 接入方式                                        | 档位从哪里来                                     | 已核对的事实                                                                                                                                                                                       |
| ----------- | ----------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | `claude -p --effort <档位>`                     | Claude Code 的模型目录，按模型列出               | 命令行自己的提示列出可接受的值：low、medium、high、xhigh、max（2.1.317，离线核对）。xhigh 在界面上叫 Extra。Opus 4.6 没有 Extra，Haiku 4.5 没有强度，以目录为准                                    |
| Codex       | `codex exec -c model_reasoning_effort="<档位>"` | Codex 的模型目录 `models_cache.json`，按模型列出 | 目录里多数模型列出 low 到 ultra 六档，Luna 系列没有 Ultra（离线核对）。命令行在本地不校验这个值，不支持的档位由服务端拒绝；Maestro 已有的处理是退回默认档并提示（`src/shared/effortRejection.ts`） |

两条产品规则：

- **单条对话**：目录里列了 Ultra 的模型就显示 Ultra，用 Codex 自己的说明（"会自动派发子任务，用量明显更高"）。它在 `codex exec` 下是否真的派发子任务没有验证，界面不额外承诺。
- **团队成员**：不提供 Ultra。理由是它会自己再派子任务，团队里会套团队，成本和调度都不受团队规则控制。这是产品选择，不是能力判断。

#### 4.1.1 计划进度从哪里来

这一节来自对一次真实验收失败的排查，全文在 03 的第 6 节。

| 工具和模型                                         | 有没有计划数据                                             | 现状                                                                                                                                | 第二轮怎么处理                                      |

## 5. 模块 B：跟进与验收清单

### 5.1 需求

| 编号 | 需求           | 行为                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1   | 跟进           | 一条对话可以登记"稍后回来"：等一段时间，或等一个应用能观察到的事件（一条命令结束、一次 CI 运行结束）。事件发生或到点时，应用往这条对话里发一回合，带上登记时写的原因和事件的结果。助手用命令登记，老板也可以在界面上登记                                                                                                                                                                                                                       |
| F2   | 跟进由应用持有 | 存在主进程并落盘。应用重启后仍然有效，到点照常触发；已过期的在启动后立即触发并说明迟到了。界面上能看到挂起的跟进（左栏这一行显示"等 CI"，右侧面板有"跟进"页），能取消                                                                                                                                                                                                                                                                          |
| F3   | 验收清单       | 一条对话可以有一组检查命令。来源：助手提议，或老板自己写。回合结束且有文件改动时，应用自己运行它们，退出码和输出存为证据，交付条显示"几条里过了几条"                                                                                                                                                                                                                                                                                           |
| F4   | 失败时怎么办   | 检查没全过，交付条不显示通过色，并问一次：把失败结果发回给助手接着修，还是我自己看。选了前者，以后这条对话不再问。接着修时每次尝试写明依据、区别和预期，按 3.1.3 判断进展：找到原因、拿到新证据、解决了一部分都算有进展，更新问题状态后继续；重复的尝试不算新办法；同一个问题连续 3 次无进展，助手先诊断再换一个有新依据的方案（3.1.4），不停下来问老板。只有下一步必须越过一条边界（总时限、承诺、新权限、新模型、本人登录）时才升级（3.1.5） |

| F6   | 三种限度       | 单次等待 20 分钟（到点回来看一眼，不停）；同一个问题 3 次无进展（诊断、换方案，不停）；总时限 2 小时，自动修复和跟进共用（硬边界）。总时限在选"发回去继续修"和登记跟进时都显示，登记跟进时写明"最迟到几点"，可以当场调整；到期时最后看一次，写下现状和推荐，停止并告诉老板                                                                                                                                                                     |

### 5.2 主流程

原型"跟进与验收"按这个流程走。

1. 助手做完改动，提议一份验收清单（例如 `npm test`、`npm run lint`）。
2. 老板在这个项目里授权一次运行检查命令，或选择不用清单。之后助手改命令，只要还在授权范围内就不再问。
3. 有清单时，应用运行检查。全过：交付条显示"2/2 通过"。没全过：显示"1/2 通过"和失败输出的结尾，按 F4 问一次。
4. 助手推送后登记跟进："CI 运行 #482 结束时回来"。卡片上写明单次等待 20 分钟、总时限和最迟时间、到期时怎么办。左栏这一行显示"等 CI"。
5. CI 结束，应用唤醒对话并带上结果。通过就结束；失败就由助手修复、再推送、再登记。
6. 没有清单时，交付条只显示改动，状态写"助手称完成"，界面不替它背书。

### 5.3 规则

- **检查命令：按项目授权一次（3.1.1）。** 第一次有检查命令时问一次"允许应用在这个项目里运行检查命令"，同意后记住。之后命令改了，只要还只在项目目录里运行、不联网写入，就不再问；要访问项目之外、联网写入或推送的命令单独请示，选项是"只允许这一次"或"不加这条检查"，不扩大授权。团队用的是同一条规则（6.9 的 R1 第 2 条）。
- **检查结果只认应用跑出来的。** 助手在回复里写"全部通过"而检查实际失败时，界面显示失败。
- **跟进必须挂在应用能观察到的东西上。** 一条命令的结束、`gh run watch` 的结束、一个时间点。应用查不到的事件不接受登记，改成定时。口头说"我在等"不算登记。
- **单次等待超时不等于停下，查询结果没变不等于失败（3.1.2、3.1.3）。** 到点事件还没发生，应用照样唤醒并附上那件事的当前状态。还在正常进行（比如 CI 在排队）就接着跟，改成较低的频率查看，同时先做不依赖它的事；多次查看结果没变仍是等待，不计入无进展。外部状态说明出了问题（被取消、报错、找不到执行的机器）才诊断。这些都在已授权的范围内，不问老板。
- **总时限是硬边界。** 到期时不悄悄继续，也不只说一句"要继续吗"：写明做到了哪、在等什么、为什么还没完、推荐怎么办，选项是"延长 1 小时"或"不再跟进"。
- **运行检查的限制。** 在对话的工作目录里运行，单条命令默认 10 分钟超时，输出按现有的工具输出截断规则存储。

| 单次等待超时                             | 唤醒并附上状态。CI 还在排队：助手改成每 10 分钟看一次，同时在本地跑同一组检查，左栏仍显示"等 CI"。之后三次查看结果不变，仍判为正常等待；CI 结束后自动收尾。不问老板                                      | CI 结果选"20 分钟到了，CI 还在排队" |

| 老板取消跟进                             | 这条跟进不再触发，对话里记一行                                                                                                                                                                           | CI 结果选"取消"                     |
| 应用重启                                 | 跟进从磁盘恢复，对话里显示一条说明，到点照常触发                                                                                                                                                         | "模拟：应用重启"                    |
| 检查命令本身跑不起来（找不到命令、超时） | 记为"没跑成"，不算通过也不算代码失败，提示检查命令                                                                                                                                                       | 未画                                |

## 6. 模块 C：团队群聊

团队群聊是第二轮必须交付的核心功能。它要做到的是：老板提出想法、选好模型和岗位，团队自己把需求写清、互相质疑、讨论并做出决定、做出来、验出来、由 PM 把住产品效果，再向老板演示。老板只在真正需要他的地方出现。

首版规模是 PM、一个开发、一个 QA。这是对规模的精简，不是对协作的精简：主动提出问题、互相质疑、讨论并形成决定、PM 的产品把关、不用催的推进，首版都要有。

### 6.1 入口

- 左栏顶部，"新建团队"和"新对话"并排。
- 命令面板里有"新建团队"；命令行是 `maestro-cli team start`。
- 它不是每次新建的默认，小任务仍然用一条对话更合适。新建时如果想法很短，给一句提示，不阻止。

### 6.2 五个对象

| 对象     | 是什么                                                                                                     | 谁拥有                         |
| -------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------ |
| 团队     | 老板提出的一件事，加上做这件事的成员、授权和预算                                                           | 应用，落盘                     |
| 成员     | 一个岗位加一条真实对话。岗位、工具、模型、档位是四个独立的选择，另可选一个替补                             | 应用。对话本身属于各家原生 CLI |
| 台账     | 这件事的全部持久事实：需求版本、基线、标准变更、讨论与决定、工作项、问题、证据、在等的事、派发记录。只追加 | 应用，落盘                     |
| 调度器   | 主进程里的一段确定性逻辑。看台账和事件，决定下一步叫醒谁                                                   | 应用                           |
| 授权范围 | 建队时老板一次给定：截止时间、回合预算、不用再问的动作                                                     | 老板                           |

分工是这样的：**调度器负责"不会停"，成员负责"想清楚"。** 调度器保证该动的人被叫醒、等的事有人跟、重启后接着走；内容上的判断，提出什么问题、同不同意、怎么改、够不够好，全部是成员的事。两者不冲突。

每位成员都是新界面里的一条普通对话，可以点进去看全过程、直接对它说话，再回到团队。事实在台账里，不在聊天里：换人、重启、给成员交代背景，传的都是台账。进度读的是台账里的工作项和证据，不读模型自己的任务清单（那个来源在一部分模型上不存在，见 4.1.1）。

### 6.3 建队

一个对话框，四组内容：

| 内容       | 行为                                                                                                                                                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 想法       | 一个文本框。写什么，团队的标题和 PM 的需求就从什么出发                                                                                                                                                                                                                    |
| 成员       | PM、开发、QA 各一行。每行选工具、模型和档位，用的是模块 A 的同一个选择器：各家用各家的说法，按模型列档位，键盘可用。团队成员不提供 Codex 的 Ultra（它会自己再派子任务）。每行可以再选一个替补，也可以不设                                                                 |
| 截止与预算 | 截止时间（可以不设）；回合预算（默认 40）。到了还没完成，团队停下来写未完成报告（6.8.3）                                                                                                                                                                                  |
| 一次授权   | 四个勾选项，默认都勾（老板 11 月 17 日确认）：在任务工作区里运行检查命令；在任务分支上提交和推送；开草稿 PR；成员出故障时用团队已选用的模型在独立的新对话里临时接任。勾了的，团队在范围内直接做，不再逐次请示；没勾的第一次用到时问一次；超出范围的按 3.1.1 和 3.1.5 处理 |

始终要老板确认的事固定写在对话框里：合并、发布、对外消息、放宽或删除标准、追加时间或预算、新的付费模型。

替补默认不设。PM 的替补说明里写清：不设替补时，故障先靠恢复会话，再按授权临时接任，都不行才问老板（6.8.2）。

对话框里对成员来源的提示只描述事实，不作保证。开发和 QA 来自同一家时写"可能有相同的盲区"；来自不同厂商时写"盲区不容易重合，但不等于结论一定对"。结论有多可靠取决于四件各自独立的事：对话是否隔离、工作区是否隔离、检查是否由应用执行、模型来源是否多样。成员面板把这四项分开列出。

### 6.4 主流程：七个阶段

| 阶段 | 做什么                                                                                                                                                                                            | 离开条件                              |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| 明确 | PM 把想法写成需求：范围、不做什么、验收标准。标准分两类：能由应用或 QA 判定的功能标准，和由 PM 对着真实产出判断的体验标准。每条写明怎么证明                                                       | 需求第一版写入台账                    |
| 质询 | 开发和 QA 同时各交一份书面意见，互相看不到。开发写不合理和做不到的；QA 写逐条的验证计划。PM 逐条回应；谈不拢的开短讨论（6.5）；归老板定的请示。阶段末尾老板确认基线，可以改、可以看差异、可以退回 | 老板确认了基线                        |
| 实施 | 开发在自己的工作区里做。QA 并行在自己的工作区里按标准准备样本和测试                                                                                                                               | 开发称完成，且应用运行的检查通过      |
| 验证 | QA 核对需要人看的标准，做探索测试。发现问题开问题单，开发修，应用重跑复现，QA 复验                                                                                                                | 功能标准都有证据，没有未关闭的问题    |
| 评审 | PM 打开真实产出，对照已确认的标准（包括体验标准）判断。不够好就打回，每条问题写位置、对应标准、影响、期待；连续两次打回触发团队复盘；之后有进展就继续修（6.7）                                    | 所有已确认的标准都有证据，PM 评审通过 |
| 演示 | 只在全部达标后出现。PM 向老板演示：先给看得见的结果和改进前后的对比，再给证据、决定和变更                                                                                                         | 演示发出                              |
| 验收 | 老板验收，或写出要改的地方。要改的话，PM 复述理解、拆成工作项，回到实施，之后再走一遍验证、评审和演示                                                                                             | 老板点了验收                          |

一次没有意外的任务，老板的操作是：确认基线、验收，再加上真正归他定的请示。额度用尽、等待超时、检查失败、反复修不好、PM 打回、连续打回后的复盘、成员故障的自动恢复，都不需要老板操作。

**任何阶段到了截止时间或回合预算而没有全部达标，都进入未完成报告（6.8.3），不进入演示。**

### 6.5 讨论：团队怎么自己想、自己谈、自己定

讨论是短的、按事件触发的、默认折叠展示的，但它是真讨论：有人提出问题，有人拿证据反对，有人被说服改主意，最后有结论和每个人的下一步。

**谁能发起，什么时候发起**

| 触发                                                                     | 发起人                         |
| ------------------------------------------------------------------------ | ------------------------------ |
| 需求有新版本                                                             | 应用（质询）                   |
| 任何成员认为有问题：需求不合理、方案有风险、标准验不了、发现了更好的做法 | 该成员，在自己的回合里提出议题 |
| 成员对另一位成员的决定有异议                                             | 提异议的成员                   |
| 成员被卡住，需要别人的信息                                               | 被卡住的成员                   |
| 同一处以同样的方式反复失败                                               | 应用叫停重复尝试，PM 组织      |
| PM 的产品评审打回                                                        | PM                             |
| 老板退回基线，或在演示时要求修改                                         | 应用，PM 组织                  |

**谁参与**：议题的负责人，加上会被结论影响的成员。不一定三个人都在。

**怎么谈：四步**

1. **各自独立写主张。** 主张、依据、什么证据会让我改主意。这一步互相看不到，避免后写的跟着先写的走。
2. **主持人给出处理建议，并说明这件事归谁定。** 主持人是议题的负责人，默认是 PM。优先找两边都能接受又不违反基线的办法。
3. **回应。** 同意、同意但留一句保留意见、或者坚持。坚持必须拿得出新证据，或者指出建议违反了基线。从这一步起，参与者能看到彼此的论据。
4. **结论。** 写进台账：结论、决定人、保留意见、每个人接下来做什么。"接下来做什么"直接变成工作项或在等的事，由调度器派发，不需要谁再转述。

**两轮是默认预算，不是终点。** 第 2 步和第 3 步算一轮，默认最多两轮。两轮之后还没谈拢时，按下面的顺序处理，而不是直接交给老板：

1. 有人拿出了新证据，或者有一个便宜的小实验能裁决（跑一次基准、试一个样本）：追加一轮或做这个实验，计入任务预算。
2. 没有新证据，而这件事可逆、在范围和预算内：负责人裁决，保留意见记入台账，这条决定标成"有争议"，演示时列给老板看。
3. 这件事不可逆，或者会改变承诺（见 6.6 的第四层）：交老板，并附上各方立场和选项。

**讨论里共享什么**：第一步之后，参与者共享这个议题的论据和摘要。不把所有聊天记录广播给所有人。

**怎么展示**：折成一行，显示议题、结论、归谁定、有没有保留意见。点开能看到四步的原话。

实测（03 的第 3.8 节）：8 次真实模型的短讨论里，4 次范围内的方案分歧全部在一轮内谈成，没有一次找老板，都找到了两边能接受的办法；4 次"两条已确认标准不能同时满足"的情形里，没有一次由 PM 自行放宽标准，3 次附上选项交给老板，1 次先去试还没试过的办法。

### 6.6 谁能定什么：四层

老板已在 11 月 17 日确认采用这组规则：事实由证据决定；范围内的实现选择和产品取舍由对应负责人听取意见后决定；改变承诺、追加预算这类事才交老板。

这组规则代替"达到共识比例就推进"。老板想从共识比例里得到的东西，人人能反对、决定做得出来、只在必要时找他，这里都保留了；去掉的只是一个对三人团队没有意义的数字。

| 层               | 是什么                                                                             | 谁定                                          | 能不能靠讨论改                                                                       |
| ---------------- | ---------------------------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------ |
| 事实             | 检查通不通过、复现成不成立、产出长什么样                                           | 证据                                          | 不能。失败的检查不会因为谁"认为可以"而变成通过                                       |
| 实现选择         | 怎么做、用什么技术、怎么测。在范围和预算内，可逆                                   | 负责人（实现归开发，测试方法归 QA），先听意见 | 能。两位非负责人都拿着证据反对时，负责人必须先做一个小实验或采纳折中，不能直接压过去 |
| 范围内的产品取舍 | 不改变已确认标准的产品判断：细节怎么取舍、体验够不够好                             | PM，先听意见                                  | 能，同上                                                                             |
| 承诺变更         | 改变核心目标、缩小已承诺的范围、放宽或删除已确认的标准、追加预算、未授权的对外动作 | 老板                                          | 团队只能提方案，不能自己定                                                           |

票数只作参考：请示卡片上列出各方立场和一行参考（例如"2 位倾向 A，1 位倾向 B"），同一家模型的一致不算两份独立意见。票数不触发任何自动推进。

三条由应用强制的硬规则：**证据否决意见**；**修的人不验**；**有结论的不重开**（对已有决定的问题再发起讨论，必须附上新证据）。

### 6.7 PM 的产品评审

技术检查通过、QA 没有发现功能错误，不等于产品达标。在向老板演示之前，PM 必须对着真实产出做产品评审。老板保留最终验收权，但不应该是唯一负责发现体验问题的人。

**判断的依据只有一条：已确认的标准是否都满足了。** 体验标准（比如 E1"同事不问你也能读懂"）和功能标准一样是承诺。PM 的评审不放过违反已确认标准的问题，也不借评审增加新要求。

| 项目                       | 规则                                                                                                                                                       |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 什么时候                   | 功能标准都有证据、没有未关闭的问题之后，演示之前                                                                                                           |
| 看什么                     | 应用采集的真实产出：渲染预览、截图、产出文件本身；有前一版时附前后对比；需要在多处查看的（比如 GitHub 和 VS Code）每处都看。不是开发的描述，也不是测试结果 |
| 结论                       | 通过，或者打回                                                                                                                                             |
| 打回时每条问题必须写       | 在产出里的位置；对应哪条已确认的标准；对用它的人有什么影响；应该是什么样                                                                                   |
| 打回的门槛                 | 只要还有一条问题违反已确认的标准，就打回，不管它看起来多小。不能把违反承诺的问题叫作"小毛病"放行，也不能自行延期（R1 第 6 条）                             |
| 不对应任何已确认标准的想法 | 列为"后续建议"，不打回，也不加进本轮。PM 认为它必须在本轮做的，按 R1 第 3 条的三个条件处理；不满足就交老板定                                               |
| 打回之后                   | 每条问题变成工作项；需要选做法时开短讨论；开发改；应用重新运行检查并重新采集产出；QA 复验受影响的标准；PM 再评审                                           |
| 什么时候通过               | 所有已确认的标准都有证据，包括体验标准。只有这时才进入演示                                                                                                 |

**连续两次打回之后：内部复盘，不放行，也不交老板。**

1. 连续两次打回触发一次团队复盘，由 PM 主持，开发和 QA 参加。
2. 复盘先查清没有收敛的原因。常见的是：标准的含义不够具体（比如没说在哪里看算数）；核对只覆盖了一部分情形；做法本身有局限；模型在这个问题上能力不够。
3. 再从授权范围内选新方案：换做法；做小实验；把问题拆成几条可以分别核对的子项（在原意之内细化标准，记入标准变更，PM 可以自己定，前提是满足 R1 第 3 条）；换已授权的替补模型。每个方案写明依据、和前两轮的区别、预期验证什么（3.1.4）。
4. 复盘必须写明下一轮出现什么变化才算有进展，例如"细化后的三条子项在两个查看器里逐条通过"。
5. 之后照常修、QA 复验、PM 复审。复审仍不通过时，按 3.1.3 判断：有进展（上一轮的问题有一条以上经 QA 核对已解决，或者拿到了能缩小原因的新证据），就继续；连续 3 轮没有进展，就再诊断一次，下一步必须有新的依据，不能是没有新证据的重复。类别可以和之前相同。复盘之后再连续两次打回，再复盘一次。
6. 只要还有已确认的标准没满足、整体预算还有、授权范围内还有有依据的下一步，就一直走这条闭环，不会自动进入演示，也不会来问老板"要不要继续改"。

**只有这些情况才停下来找老板：**

- 到了截止时间或回合预算：写未完成报告（6.8.3），由老板决定追加、接受遗留项还是停止。
- 下一步必须越过一条边界：比如剩下的方案都要改变承诺（放宽或移出某条标准）、需要新模型或新权限、需要老板登录。卡片格式按 3.1.5，写明是哪条边界、为什么授权内没有路了。

老板能随时看到 PM 看的是什么：右侧"产出"页显示同一份真实产出。

实测（03 的第 3.8 节）：给 PM 一份检查全过、QA 全过但读起来很差的真实产出，两家模型 12 次全部打回，问题具体，绝大多数落在已确认范围内。这说明模型能发现体验问题。它没有验证连续几轮修改之后的收敛行为，也不能用来支持"打回几次就放行"。第四批探针同时换了对照样本和评审提示，好产出通过率的变化不能只归因于提示里的门槛。

### 6.8 不停住、不反复请示

#### 6.8.1 团队里的等待、无进展和预算

规则见 3.1.2 至 3.1.5，团队的具体做法：

|            | 单次等待超时                                                                   | 同一个问题三次无进展                                  | 截止时间或回合预算用完               |
| ---------- | ------------------------------------------------------------------------------ | ----------------------------------------------------- | ------------------------------------ |
| 例子       | CI 等了 20 分钟还在排队                                                        | 问题 #1 修了三次，复现结果一模一样                    | 18:00 到了，E1 还没通过              |
| 应用做什么 | 叫醒登记的成员，附上那件事的当前状态                                           | 停止重复派发，请 PM 主持复盘                          | 停止派发新回合，生成未完成报告的框架 |
| 团队做什么 | 正常排队就接着跟，改成每 10 分钟看一次，同时先做不依赖它的事；状态异常就查原因 | 复盘：查原因、选有新依据的方案、写下一轮的进展证据    | PM 写推荐                            |
| 找不找老板 | 不找                                                                           | 不找。有进展就继续；下一步必须越过边界才升级（3.1.5） | 找。追加、接受遗留项或停止           |

**已经授权的事不重复请示。** 建队时勾了的动作，团队在范围内直接做，应用按授权执行并留记录。没勾的动作第一次用到时问一次，问得具体（推到哪个分支、会不会碰 main、不做会怎样），同意后同类不再问。

**额度用尽不停工。** 成员的额度用尽时：设了替补的，替补直接接手，拿到的是台账和工作区现状；没设替补的，这位成员的工作挂起到额度恢复，其他成员继续，恢复后应用自动叫醒。这是一次正常等待，不是失败。两种情况都只出一张说明卡片，不出需要操作的卡片。派发前先看用量采样，已经用尽就直接走这条路，不白跑一回合。

#### 6.8.2 成员故障的恢复

成员（尤其是 PM）出故障时，应用先分清是哪一种，再按有限、可观察的步骤恢复。已经完成的动作通过台账和派发记录识别，不会重做。

| 状态               | 怎么判断                                         | 应用做什么                                                                     |
| ------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------ |
| 正常工作，还没结束 | 进程在，10 分钟内有输出                          | 等。不算故障                                                                   |
| 回合失败           | 进程异常退出、接口报错、被看门狗停掉             | 先核对已有结果；再带"上一次可能做了一部分"重试同一回合一次                     |
| 漏报               | 回合正常结束，但没有报告块                       | 先按看到的事实记账；再请它只补报告，不重做                                     |
| 报告格式错误       | 有报告块，但解析或校验失败                       | 把具体错误给它，请它只重交报告，一次                                           |
| 会话损坏           | 原生会话无法续接（文件损坏、找不到、上下文溢出） | 用同一个模型新开一条对话，交给它台账切片和最近的决定                           |
| 模型暂时不可用     | 用量上限、服务报错，有恢复时间                   | 不重试同一个模型；按下面的顺序接任                                             |
| 登录失效           | 错误识别为认证失败                               | 只有老板能登录。其他成员继续；按下面的顺序临时接任；同时告诉老板缺的是哪个登录 |
| 空转               | 回合结束、报告合法，但台账没有任何变化           | 算一次无进展。第一次指出它缺什么；连续两次进入诊断                             |

**接任的顺序**（模型暂时不可用或登录失效时）：

1. 已授权的替补（建队时给这个岗位选的）。
2. 用团队已选用的模型新开一条对话临时接任。这是建队时的一项授权，默认打开。新开的对话不和其他成员共用；优先选和开发不同家的模型。原来的模型恢复后自动换回。
3. 前两步都不可用（没设替补，也没有授权临时接任）时，等原来的模型恢复是一次正常等待：没有设截止时间，或者恢复时间早于截止时间，团队就自己等，其间只做不需要 PM 的事，不问老板。
4. 只有等恢复会错过截止时间时，剩下的每条路都要越过一条边界（临时接任要新权限，等恢复要追加时间），才出升级卡片，写明这两条边界和各自的代价。需要新的付费模型时，卡片写明是哪个、为什么。

没有替补不等于没有恢复办法：会话损坏时从台账新开对话就能恢复，不需要替补。

**PM 不可用时，应用自己负责呈现现状。** 团队主视图出现一张"由应用根据台账生成"的现状卡片：几条标准有证据、哪些没有及原因、未完成的工作项、在等的事、已用预算。到了截止时间而 PM 仍不可用时，未完成报告同样由应用从台账生成。发给 PM 的消息排队，恢复后送达。

#### 6.8.3 截止、预算与终态

到了截止时间或回合预算，而已确认的标准还没有全部满足时：

1. 应用停止派发新回合（回合预算用完时，生成报告不再消耗回合）。
2. 生成未完成报告，标明"这是进度报告，不是完成演示"。内容：做到了什么（附真实产出）；哪些已确认的标准没有证据，每条的原因；团队试过什么；推荐。
3. 老板三选一：追加时间或回合（推荐时写明还差多少、预计多久）；接受这些遗留项并验收；停止，保留分支和台账。
4. 终态按 3.1.6 记录。接受遗留项时，遗留项仍标为未达标，进入后续清单，负责人由老板安排；验收不会把它们改成通过。

演示卡片只在全部达标、PM 评审通过时出现。未完成报告和演示用不同的卡片和用词，不会混淆。

### 6.9 规则

每条后面标了它来自哪里：**实测**指 03 里的真实运行，**设计**指推理得出、还没有被运行检验。

#### R1 标准和承诺不能被悄悄改掉

1. **基线只有老板能确认，而且确认的不只是标准。** 确认卡片同时列出范围、本轮不做什么、每条标准和证明方式、检查命令的试跑结果。老板可以直接改某一条、看它和上一版的差异、写一句意见退回给团队重新讨论。确认之后的每一处改动都记在"标准变更"里。（实测：一次运行里 PM 把一类写法划进了"不做"，脚本里的老板没看就确认，交付因此变窄。03 的第 3.6 节）
2. **检查命令：授权一次，规则一处。** 建队时的"运行检查"授权覆盖"在任务工作区内运行团队提出的检查命令"。有这项授权：应用在确认基线之前先试跑，试跑结果放在基线卡片上，命令本身跑不起来的不能进基线。没有这项授权：命令先逐条列在卡片上由老板批准，批准后再试跑，然后才确认基线。此后同一类命令不再问；要访问工作区之外或要对外写入的命令才单独请示。单条对话用同一条规则，授权按项目记住。（实测：实验里一条跑不起来的命令被当成缺陷空转了几轮；加上试跑后被拦下）
3. **团队自己加严或新增标准，要同时满足三条。** 属于已确认的想法和标准的合理含义；开发估的额外成本在剩余预算之内；不影响截止时间。三条都满足，PM 可以直接定并记入标准变更，其他成员可以提异议。任何一条不满足，就是扩大范围，要老板批。（设计）
4. **放宽、删除、改证明方式、改已有标准的示例或数值，要老板批。** 卡片内容固定：改动前后对照；这条标准当前的检查结果；其他成员的意见；如果这条标准此刻正在失败，标出来。老板不批，旧标准继续有效。（设计。实测参照：6 次"检查一直不过"的探针和 4 次"标准冲突"的讨论里，没有一次模型自行改掉标准）
5. **老板自己改范围，直接生效。** 在群里说一句，或对某位成员说，都算。记入标准变更，来源写明是老板。对某位成员说的要求由该成员报给 PM 记账，成员不能自己悄悄改范围。
6. **已经承诺的要求不能因为被定成"一般"或"轻微"就自行延期。** 问题单必须写明它违反的是哪条已确认的标准。违反已确认标准的问题，不论严重程度，只有两条路：修好并复验，或者由老板批准变更。严重程度只用来排修复的先后。PM 能自行延后的只有不触及任何已确认标准的发现，比如改进建议，记为"后续建议"，列在演示和终态里。产品评审同样适用这条：违反已确认标准的问题不能叫作"小毛病"放行（6.7）。（设计）
7. **演示和报告不能只报喜。** "几条有证据"的计数由应用按证据生成，PM 改不了。演示只在全部达标时出现；没达标时出的是未完成报告，列出没有证据的标准和原因。两者都要列出基线后的全部标准变更和有争议的决定。（实测：6 次截止压力下的探针和 4 次完整循环的演示，没有一次把没过的标准写成通过）
8. **证据要能证明它对应的那句话。** "正常渲染"要有渲染预览或截图，格式检查证明不了它。界面和体验类的问题单可以是复现步骤、截图和操作记录，不要求一定是一条命令或一个测试。（设计）
9. **证据不能被稀释。** 应用记录每次检查跑了多少条测试。数量变少、跳过的变多、命令文本变了，都标出来并进入演示。（设计）
10. **标准本身有问题时，走标准变更，不派给开发。** 任何成员发现标准自相矛盾、无法判定，报成"标准问题"，直接到 PM。（实测发现的缺口；规则本身还没有被运行检验）

#### R2 QA 独立于开发

1. **各有各的工作区。** 开发的工作区只有开发能写。QA 的工作区里 QA 只能写 `qa/`。PM 对两边只读。（实测：四次运行里 9 个可以写文件的 QA 回合，没有一次越界）
2. **越界由应用还原**，并记一次违规。（设计）
3. **QA 的质询产出是验证计划。** 每条标准写怎么验、要什么样本。写不出怎么验的标准自动成为一条意见。（实测：不这样要求时出现过空意见；这样要求后 9 条标准全部有计划）
4. **QA 的依据是标准和真实产出，不是开发的代码。** 实施阶段 QA 看不到开发没做完的改动。（实测）
5. **问题单必须能重现**，并写明违反哪条标准。形式见 R1 第 8 条。（实测：四次运行的 6 张问题单全部能重现）
6. **修的人不验。** 开发称修好后，应用先自己重跑复现，再叫 QA 复验。只有 QA 能把问题关掉。（实测）
7. **开发说"没法修"时不叫 QA 复验**，直接到 PM 分诊。（设计）
8. **没发现问题也要给证据**，否则这条标准停在"待证明"。
9. **来源相同只作提示。** 开发和 QA 来自同一家时，界面提示"可能有相同的盲区"。它不改变隔离和证据的事实，也不阻止建队。
10. **QA 的测试是交付的一部分。** 验收后 `qa/` 随分支保留。

#### R3 不停住，不重复做，不把困难退给老板

1. **总有一件事在发生。** 任务没有结束也没有暂停时，下面三样至少有一样：一位正在工作的成员；一件登记过、在等的事；一张等老板操作的卡片。三样都没有，调度器叫醒 PM。两条路径分别保证时限：回合结束、检查结束等事件到来时，调度器在 5 秒内处理；万一漏掉事件，调度器每 30 秒自查一次兜底。所以任何时候出现"三样都没有"，最迟 30 秒内会被发现。（设计。参照：旧群聊里说"等 CI"后没有任何东西叫醒它）
2. **嘴上说等不算等。** 等待必须登记，而且挂在应用能查到的事上。（实测：一家模型会照提示报告一个并不存在的等待）
3. **等待超时、没有进展、预算用完，按 3.1 和 6.8.1 处理。**
4. **漏报先补报。** 成员的回合结束却没有交报告时：应用先按自己看到的事实记账，再请它只补报告、不重做。还没有，就把它最后的回复交给 PM 整理。同一位成员连续两次这样，PM 提议换上替补。（实测：39 个真实回合没有出现漏报；探针里丢掉报告后补报 4/4 成功，没有动文件）
5. **派发先记账，再执行。** 重启后对每个没结束的回合：先看那位成员的工作区和原生会话里有没有结果，有就收下；没有才重新交给它，并写明"上一次可能做了一部分"。（实测：探针里中途杀掉再重派，4/4 没有重做已有的部分）
6. **重启之后自动接着走**，对话里说明一句。团队和登记过的等待都是老板明确要它自己推进的。
7. **成员故障，按 6.8.2 恢复。** 先分清是正常工作没结束、回合失败、漏报、报告格式错误、会话损坏、模型不可用、登录失效还是空转；再按有限的步骤恢复：核对已有结果、补报告、重试一次、从台账恢复会话、已授权替补、按授权临时接任；都没有时，等恢复不越过截止就等。剩下的路都要越过边界才提出具体请求。PM 不可用时，现状和到期报告由应用从台账生成。（原型已验证两种故障；真实恢复在开发阶段验收）
8. **到了截止或预算，写未完成报告。** 见 6.8.3。

#### R4 成本有刹车

1. **上限是用来防空转的，不是用来把事情交给老板的。**

| 项目                 | 默认                                                                 | 到了之后                                            |
| -------------------- | -------------------------------------------------------------------- | --------------------------------------------------- |
| 同时工作的成员       | 2                                                                    | 排队                                                |
| 一个议题的讨论       | 2 轮                                                                 | 按 6.5 的三步处理                                   |
| 同一个问题连续无进展 | 3 次                                                                 | 诊断，换一个有新依据的方案；再连续 3 次无进展再诊断 |
| PM 连续打回          | 2 次                                                                 | 团队复盘，之后有进展就继续修；再连续两次打回再复盘  |
| 相同的尝试           | 没有新证据就不执行第二遍；同一类别可以用多次，每次写依据、区别、预期 | 重复的尝试计一次无进展                              |
| 升级                 | 只在下一步必须越过边界时（3.1.5）                                    | 卡片写明边界、授权内每条路的结论、选项和推荐        |
| 单次等待             | 20 分钟                                                              | 回来看一眼，接着跟                                  |

2. **PM 不当传话筒。** 成员之间的常规流转由调度器按台账直接完成。PM 的回合用在判断上：写需求、回应意见、主持讨论、分诊、产品评审、演示。（实测：四次运行里 PM 占输入的 4% 到 13%；旧群聊里主持人占 86%）
3. **每回合的输入是台账切片**，加上所在议题的论据，不是全部聊天记录。
4. **团队成员不用 Codex 的 Ultra。**
5. **结束时给账单**：每位成员的回合数、用量、用时。

### 6.11 界面

**团队主视图**要让老板不读长文就知道五件事：现在的产出、团队在解决什么、定了哪些事、下一步是什么、需不需要我。

- **顶部两行。** 第一行是七个阶段和"需要你"的计数。第二行是四格：现在、在解决、下一步、产出（一个链接，打开真实产出）。
- **中间按时间排，但默认是摘要。** 已经过去的阶段各收成一行，点开才展开。讨论、检查结果、标准清单默认折成一行，显示结论。需要老板操作的卡片是唯一带强调色的东西，同一时间只突出一个可操作的问题。
- **演示卡片先给结果。** 只在全部达标时出现。最上面是真实产出的预览，可以切换改进前后，下面是三行"对用它的人来说变了什么"。标准、决定、变更、代码改动收在下面，点开才展开。
- **未完成报告和演示长得不一样。** 未完成报告的标题写"未完成报告"，旁边标"这是进度报告，不是完成演示"，按钮是追加、接受遗留项、停止三项，没有"验收"。
- **终态写在顶部。** "已验收：全部达标"、"已验收，接受了 N 项遗留"、"已停止：未完成"三种，"在解决"一栏在后两种里列出没达标的标准。左栏的团队行同样区分。
- **只有需要老板的卡片带强调色。** 已经回答过的卡片去掉强调色。
- **输入框。** 默认发给 PM，输入 @ 列出成员，方向键和回车可选。每条消息下面有送达状态（成员正忙时显示"排在它当前回合之后"）和处理结果，回复里写明影响了哪些成员、哪些标准和工作项。
- **成员怎么认。** 每位成员有固定的形状标记和岗位名，后面跟模型名；同一位成员在群里、左栏、讨论里都是同一个标记。状态用文字，不只靠颜色。

**成员对话**：点左栏的成员进入。顶部是返回团队的入口、成员的模型和档位、工作区和权限。内容是应用每一步交给它的事和它的回复。在这里说的话团队里也能看到。Esc 回到团队，焦点回到左栏那一行。

**右侧面板六页**：产出（真实产出和改进前后）、进展（工作项、问题、在等的事）、决定（团队的决定、老板的决定、标准变更）、证据（按标准列，写明证据是谁给的）、成员（模型、档位、替补、可靠性的四项、授权与预算）、改动（沿用现有改动面板）。默认界面不出现内部实现用语。

**键盘与焦点**：对话框打开时焦点进第一个输入，Tab 不会跑出对话框，关闭后焦点回到打开它的控件。选择器的方向键、Tab、回车、Esc 和模块 A 一致，Esc 只关选择器。展开或收起一处内容不改变滚动位置，也不重播进入动画。

**状态用词固定**：

| 用词                       | 含义                                 | 谁能写           |
| -------------------------- | ------------------------------------ | ---------------- |
| 成员称完成、已修复（自述） | 成员自己说的                         | 该成员           |
| 检查通过                   | 应用运行了检查                       | 应用             |
| 已复验                     | 另一位成员按复现确认过               | 修复者之外的成员 |
| 评审通过、评审打回         | PM 对着真实产出的判断                | PM               |
| 已验收：全部达标           | 全部有证据，老板点了验收             | 老板             |
| 已验收，接受了 N 项遗留    | 老板在未完成报告上接受了列出的遗留项 | 老板             |
| 未达标（已接受）           | 遗留项在台账里的状态，不会变成通过   | 应用             |

### 6.12 成员怎么和台账交互

- **写：回合结尾的报告块。** 每位成员每回合的回复以一个 `team-report` 代码块结尾，内容是 JSON，类型随回合而定：需求、意见、主张、处理建议、回应、实现、验证、修复、复验、产品评审、演示，以及"提出议题"。应用解析它，按身份校验权限，再写入台账。（实测：39 个真实回合全部一次交出合格报告）
- **读：命令行。** 成员需要台账细节时用 `maestro-cli team status`、`team show`。可选，每回合的输入已经带了它需要的切片。
- **老板和脚本：命令行对等。**

### 7.4 前置条件

- 最大的技术风险：调度器在主进程，对话的启动在所属窗口的渲染进程。做法是调度器经现有的派发通道把回合送进对话的队列。模块 B 的跟进会第一个用到它，所以风险在团队之前暴露。

## 10. 风险与没有验证的部分

详见 [03-verification.md](03-verification.md) 的第 8 节。影响评审判断的四条：

1. **三种状态要分清：原型已验证、规则已定义、开发阶段验收。** 原型 P7.1 用模拟数据和模拟回复验证了流程和界面讲得通（147 项自动检查和逐屏走查，其中升级条件的检查直接验证判断函数和界面状态）。真实调度、持久化恢复、模型接替、权限执行在产品里都还不存在，要在 M1 到 M3 逐段由工程做集成验收。模拟结果不代表真实模型或真实产品已经通过。
2. **真实模型实验样本小。** 4 次完整循环、68 次单回合或单议题探针，只有 Claude Sonnet 和 Codex GPT-6.1-Sol 两个模型，都在低强度下。PM 能发现体验问题有数据；连续几轮修改之后能不能收敛没有数据。
3. **团队适合什么样的任务、岗位怎么配最好，还没有足够的数据。** 这不影响团队群聊是必须交付的核心功能；它影响新建时给什么提示、默认怎么配。中等任务上的同条件对照排在路线图里。
4. **一部分规则只有设计。** 见 6.10 里标为"规则已定义"的行，以及标准问题走标准变更、有争议的决定。
5. **"重复的尝试"在真实产品里怎么比对，要在开发阶段定细节。** 原型里用写好的改动标识比对；真实产品里要从改动的文件和内容、实验的命令和结果生成可比对的标识，并处理"内容相近但不完全相同"的情形。推荐先按改动内容和失败签名严格比对，宁可漏判重复（多花一次尝试）也不误判（把新办法当重复拦掉），漏判的代价由无进展计数和整体预算兜住。
