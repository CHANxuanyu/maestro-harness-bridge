## 结论

1. **团队群聊是第二轮必须交付的核心功能。** 首版是 PM、一个开发、一个 QA。精简的是规模，不是协作：团队会自己提出问题、讨论并做出决定，PM 对产品效果把关，全程不用催。
2. **团队自己定范围内的事，只把该你定的交给你。** 四层决定：事实不能靠讨论改；实现选择和范围内的产品取舍由团队讨论后自己定；改目标、缩范围、放宽标准、追加预算才找你。
3. **PM 在演示之前把关，而且不会因为打回次数多就放行。** 检查全过、QA 没发现错，不等于产品达标。PM 对着真实产出评审，每条问题对应已确认的标准；连续两次打回，团队内部复盘、换打法；有进展就继续修。只有全部达标才向你演示。
4. **不停住，也不反复请示，单聊、团队和 PM 评审一个规则。** 单次等待超时后接着跟；查询结果没变不算失败；防的是没有新证据的相同尝试，不是某类办法用了几次；有进展就更新问题状态继续；三次无进展先诊断、换有新依据的方案；成员故障按顺序自动恢复；授权过的动作不再问。只有下一步必须越过预算、承诺、新权限、新模型或你的登录这几条边界，才找你，而且写明是哪条边界、给具体选项。
5. **结果如实。** 到了截止还没做完，给你的是未完成报告，不是完成演示。接受遗留项后，遗留项仍标为未达标并进后续清单；统计按实际路径算。
6. **日常界面的问题是信息排位。** 一个高度不变的活动条，状态只画一处，红色只给真失败。模型和强度用厂商自己的说法，按模型。
7. **跟进、检查运行这些基础能力只做一次，团队和单条对话共用。** 开发顺序上，团队是主线，第一段就跑通一条最小的完整流程。
8. **两条新机制用真实模型试过，是走得通的，但样本小。** 差的产出 12 次全部被 PM 打回；范围内的分歧 4 次全部由团队自己谈成；触及承诺的 4 次没有一次自行放宽标准。产品里的团队群聊还不存在。
